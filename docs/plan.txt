# HaalKhata — Splitwise Clone: Architecture Plan (v4)

## Context

Greenfield build. Goal: a fully web-hosted Splitwise clone — responsive on
mobile and desktop browsers — with an AI feature that turns an uploaded
receipt photo into itemized line items (with tax + tip) that can be assigned
to people. Supports one-off spending and groups (trips, home, etc.), all core
Splitwise features, and a clean schema-first API contract so a native mobile
app can reuse the backend later. Direct payment settlement is deferred;
recording settlements is in.

**Decisions locked with the user (v3 — supersedes v2):**
- **No vendor lock-in, full control (v3).** Deploy target is a self-hosted
  Docker host (any VPS), NOT Vercel. Managed services are allowed only
  behind swappable interfaces or a plain connection string.
- **Database: Postgres from day one (v3 — replaces SQLite).** No SQLite
  anywhere. Local dev and prod both run vanilla Postgres (dev via
  `docker compose up db` or any local Postgres; prod via the compose file).
  The repo layer stays the only place SQL lives; the driver is `pg`
  (node-postgres), no ORM.
- **Schema as versioned SQL migrations (v3.1).** The schema is defined in
  plain `.sql` files under `apps/web/migrations/` run by node-pg-migrate
  (history table `pgmigrations`). Pending migrations auto-apply once per
  process on boot (db.ts), so dev and Docker stay zero-step; the CLI
  (`pnpm db:new`, `pnpm db:migrate`, `pnpm db:down`) is for authoring and
  rollback. No inline DDL in code.
- **Backend: Node/TypeScript inside Next.js** (no Go, no Fly.io). One
  language, one deploy artifact (Next standalone output in Docker).
- **API contract: ConnectRPC + Protobuf stays.** `.proto` files remain the
  single source of truth; `buf` + `protoc-gen-es` generate the TypeScript
  messages and service descriptors used by BOTH the server handlers and the
  web client. A future mobile app regenerates a Swift/Kotlin client from the
  identical protos and calls the same `/api/connect/*` endpoints — one
  contract, no drift, no rewrite.
- **Storage:** repository layer (`/repo`) owns ALL SQL — Postgres via `pg`,
  async throughout. Because no SQL leaks outside `/repo`, changing hosts is
  a `DATABASE_URL` change; there is nothing provider-specific to migrate.
- **Auth:** email *or phone* + password with signed bearer tokens (see §4b).
  Login RPC sets an httpOnly cookie (web) and returns the token in the
  response body (mobile). Every RPC accepts either the cookie or
  `Authorization: Bearer`.
- **AI receipt parsing: no vendor lock.** Provider abstraction with
  config-driven ordering: self-hosted vision box (OpenAI-compatible, e.g.
  Ollama/vLLM + Qwen2.5-VL behind Cloudflare Tunnel) → cloud API (Claude
  vision) → mock provider (deterministic demo data so the flow always works).
  Dev default: cloud-first. Prod: local-first with cloud fallback.
- **Notifications:** in-app notifications now; Web Push (VAPID) + email
  (Resend) are a later phase (need keys/infra).

## Goal / Deliverable

A working app where a real user can: sign up / log in, create groups and add
members by email (even before they sign up — "shadow users" claim their
account at signup), add expenses with any split type (equal, exact amounts,
percentages, shares, itemized), record multiple payers, scan a receipt photo
into an editable itemized draft and tap-assign items to people (tax + tip
split proportionally), see who owes whom per group and overall, simplify
debts (min cash flow), record settlements, comment on expenses, see an
activity feed and in-app notifications — responsive on mobile + desktop,
installable PWA shell.

Explicitly NOT in v1: payment rails, FX conversion, native mobile app
(contract-ready only), SMS, Web Push/email delivery.

## 1. Architecture Overview

```
Browser (mobile + desktop)                       future native app
   │  typed Connect client (gen TS)                 │  generated Swift/Kotlin client
   ▼                                                ▼
/api/connect/*  ── ConnectRPC over HTTP (JSON/binary) ── one contract from /proto
   │
   ▼
apps/web/src/server/api/connect/   handlers: transport concerns ONLY
   │                               (decode, auth context, map errors)
   ▼
apps/web/src/server/usecase/       ALL business logic (split math, balances,
   │                               debt simplification, validation, activity)
   ▼
apps/web/src/server/repo/          ALL SQL (Postgres via pg)
```

Layering rules (enforced by review):
- `api/connect` handlers: no SQL, no business logic. Decode request → call
  usecase → encode response. `routes.ts` wires services to the router.
- `usecase`: pure TypeScript business logic. No SQL, no transport types
  beyond the generated proto messages. Domain math (splits, balances,
  simplify) lives in `usecase/domain/` (balances) and
  `@haalkhata/shared/expense/` (splits) as pure functions — unit tested.
- `repo`: SQL only. No business decisions.

## 2b. Shared client package (v5 — 2026-07-26)

`apps/web` and `apps/mobile` are both TypeScript clients of the same contract,
so a class of client-side code is genuinely common to them: the React Query key
registry, the cents-based money helpers, and the greeting helper. These were
originally duplicated file-for-file, kept in sync by an AGENTS.md instruction
telling humans to keep them byte-identical. Nothing enforced it, and silent
drift in `queryKeys.ts` produces stale-cache bugs that are near-impossible to
reproduce.

**Decision:** the duplicated files move to `packages/shared`
(`@haalkhata/shared`), a hand-written workspace package consumed by both apps —
converting a discipline problem into a compiler problem.

```
/packages/shared/
  src/api/queryKeys.ts         query-key registry + MONEY_KEYS invalidation set
  src/money/money.ts           formatMoney / parseMoneyInput / centsToInput / todayISO
  src/money/money.constants.ts CURRENCIES, CATEGORIES
  src/money/money.test.ts      colocated unit tests (vitest)
  src/expense/allocate.ts      allocate() — largest-remainder cent allocation
  src/expense/splits.ts        computeSplits / computeItemizedSplits (+ tests)
  src/greeting.ts              time-of-day greeting
```

**Amendment (v5.1 — 2026-07-26):** the split math moved here from
`apps/web/src/server/expense/domain/`. It is the one exception to "client
code": the SERVER usecase imports it too. The reason is the itemized editor
(§3b) — it shows a live per-person total as you fill the grid, and that figure
has to be the figure that gets saved. Re-implementing largest-remainder
allocation in the client would put cent-exact money logic in two places, which
is exactly the drift this package exists to prevent. Balance math
(`pairwiseBalances`, `simplifyDebts`) stays in `server/expense/domain/` — the
client has no use for it.

- Consumed as `@haalkhata/shared/<subpath>` (subpath exports mapping straight
  to `./src/*.ts`, exactly like `@haalkhata/protogen`). Raw TypeScript, no
  build step — Next transpiles it via `transpilePackages`, Metro via the
  existing workspace `watchFolders`.
- **Admission rule:** only code that is (a) pure TypeScript, (b) free of React,
  React Native, DOM and Node APIs, and (c) actually needed by both apps. UI
  primitives stay per-app (they render to different renderers); the Connect
  transports stay per-app (cookie auth vs bearer auth).
- Its own quality gates (`typecheck` / `lint` / `test`) run from the root
  alongside the app gates, so the shared code is held to the same
  id-length + JSDoc conventions as everything else.

## 3. Frontend structure (per route)

```
src/app/<route>/
├── page.tsx                  # THIN orchestrator: params, providers, render
├── loading.tsx               # Route-level loading UI
├── types/ constants/ hooks/ utils/   # Route-scoped; tests colocated in utils/
└── components/
    └── <PageComponent>/
        ├── <PageComponent>.tsx   # component orchestrator: ONE composite hook,
        │                         # assembles sub-trees, owns fallbacks
        ├── hooks/                # useXAPI (all React Query calls), useXState,
        │                         # useXHandlers, composed by useX
        ├── utils/                # pure helpers
        └── components/           # sub-components repeating this structure
```

- Data: TanStack Query wrapping the typed Connect client (`useXAPI` hooks own
  every query/mutation; components never call the client directly).
- Tooling: ESLint (flat config + next + typescript rules), react-doctor scan,
  vitest for domain/unit tests, `buf lint` + `buf breaking` for the contract.
- Naming/docs (mandated 2026-07-12): every identifier ≥ 4 characters, no
  abbreviations (enforced by eslint `id-length`; DB-column/proto property
  names exempt); every file has a header doc comment; every exported symbol
  and non-trivial internal function carries JSDoc (@param/@returns).
- Constants (mandated 2026-07-12): never inline between functions. Server:
  one `<domain>.constants.ts` per domain (auth, group, expense, receipt,
  common/db, api/connect). Frontend: route-scoped constants in the route's
  `constants/` folder; shared constants in the owning folder's
  `*.constants.ts` (e.g. components/ui/ui.constants.ts, lib/money/money.constants.ts).
  Live objects (handlers, provider impls, clients) are not constants and
  stay where they are.

## 3b. Itemized split editor (v5.1 — 2026-07-26)

Until now `split_type=itemized` could only be produced by the receipt scanner:
the expense form offered equal/exact/percent/shares, and the line-item editor
lived behind a photo upload on /scan. Splitting a bill by item without
photographing a receipt was impossible. The form now has a fifth **Itemized**
tab (`app/(app)/expenses/new/.../ItemizedEditor/`).

**Shape: a grid, items × people.** Rows are line items (name + amount),
columns are the people in the context, and a cell is that person's share of
that item. Tax and Tip are rows in the same grid; a totals row runs along the
bottom. This mirrors the one itemized UI its users call "nearly ideal" —
Splitwise's web view — whose praised properties are tabular entry, single-screen
person assignment, editable items, and tips as percentages.

**Interaction decisions, from UX research on bill splitters:**
- **New items arrive shared by everyone.** Splitting across the whole table is
  the common case, so it costs zero taps and the user only touches exceptions.
  Starting from an empty grid made a 10-item / 4-person bill cost ~40 taps.
- **Cells are toggles, not inputs.** The binding constraint is cognitive load
  (a receipt has 12–20 lines; working memory holds ~7), so the default mode is
  tap-to-include, never type-a-number.
- **Uneven shares are a mode, not the default.** A checkbox swaps the cells to
  integer weight inputs for "she had two, he had one". Weights are the existing
  `expense_item_assignments.weight` column — no schema change.
- **Live per-person totals.** The bottom row shows what each person currently
  owes, recomputed on every keystroke via the shared `computeItemizedSplits`
  (§2b amendment) — the preview is the saved figure, not an approximation.
- **Tip presets** (10/15/18/20% of the items subtotal) alongside the raw input.

The Amount field at the top of the form becomes a read-only readout of
items + tax + tip while this tab is active; the server independently recomputes
that sum and rejects a mismatch.

Editing an existing itemized expense is still blocked (unchanged) — the guard
in NewExpensePage stands until the editor can round-trip saved items.

## 4. Data Model (integer cents everywhere, soft-delete on expenses)

users (shadow users: password_hash NULL, claimable at signup) · friendships ·
groups · group_members · expenses (group_id NULL ⇒ one-off; split_type:
equal|exact|percent|shares|itemized; tax/tip cents for itemized) ·
expense_payers (multi-payer) · expense_splits · expense_items ·
expense_item_assignments · settlements · comments · activity · notifications.

Balances are computed, not stored (derive from splits + payers −
settlements). Single currency per group; currency code stored.

## 4b. Account identifiers: email OR phone (v5.2 — 2026-07-26)

An account is reachable by **email, phone, or both** — the original
email-only assumption is gone (migration `1784073600000_add_user_phone`).

- `users.email` is nullable, `users.phone` is E.164 with a partial unique
  index (`WHERE phone IS NOT NULL`, so multiple NULLs are fine), and a
  `chk_users_has_identifier` CHECK guarantees at least one is present.
- Phone is normalized with `libphonenumber-js` (`normalizePhone` in
  `auth.constants.ts`) and only ever stored in E.164, so lookups are exact.
- **US-first, not US-only.** `normalizePhone` passes
  `DEFAULT_PHONE_REGION = "US"`, so national formats — `(617) 555-1212`,
  `617-555-1212`, `6175551212` — resolve to +1. Any number written with an
  explicit `+<country>` is still honored, so international users are never
  blocked. Without that default argument libphonenumber-js accepts ONLY
  `+`-prefixed input and silently rejects every national format, which is how
  this shipped until 2026-07-26. Rejections now return `PHONE_FORMAT_HINT`,
  which names the accepted shapes instead of a bare "invalid".
- Auth RPCs take `email` and `phone` fields with exactly one populated; the
  account is looked up by whichever was supplied.
- **Shadow users may be phone-only.** Inviting someone by phone creates a
  claimable row with NULL email, claimed at signup by that phone the same way
  an email invite is (`findOrCreateUserByPhone`, mirroring the email path
  including its unique-violation retry).
- Clients present **one "email or phone" field**, not two. The raw string is
  routed by `splitIdentifier` (`@haalkhata/shared/auth/identifier.ts`): an `@`
  means email, anything else is sent as phone for the server to validate. It
  lives in the shared package because login, signup and friend-invite on both
  apps all need identical routing.

Group invites (`AddMember`) remain email-only for now — the same treatment
applies whenever that flow is revisited.

## 5. Core Domain Logic (usecase/domain — pure, unit-tested)

- `allocate(total, weights)` — largest-remainder allocation; splits always
  reconcile to the exact cent total, deterministic remainder assignment.
- Split calculators: equal / exact (validate sum) / percent (basis points,
  sum=10000) / shares / itemized (Σ assigned items + proportional tax + tip).
- Pairwise balances: per-expense net (paid − owed) matched deterministically
  into debtor→creditor entries; settlements subtract; normalize per pair.
- Simplify debts: greedy min-cash-flow over net balances.

## 6. AI Receipt Pipeline (usecase/receipt + provider adapters)

Upload photo → `ParseReceipt` RPC → provider failover chain (config env
`RECEIPT_AI_PROVIDERS`, default `anthropic,local,mock`; prod
`local,anthropic,mock`) → normalized `ParsedReceipt {merchant, date,
currency, items[], subtotal, tax, tip, total}` → editable review/assign UI →
saved as `split_type=itemized` expense. AI output is never auto-committed.
Local provider speaks the OpenAI-compatible vision wire format (swap base
URL); cloud provider uses the Claude API with a strict JSON schema.

## 7. Delivery Phases

- **Phase 0 — Foundations:** monorepo, buf codegen wired, Postgres schema
  (bootstrap on startup), auth (signup/login/claim shadow accounts), Connect
  endpoint mounted, app shell + login, ESLint/vitest/react-doctor.
- **Phase 1 — Expense engine:** groups + members, expenses (all split
  types, multi-payer), balances + simplify, settlements, activity feed.
- **Phase 2 — AI receipt itemization:** ParseReceipt + failover providers,
  review/assign UI, itemized save.
- **Phase 3 — Social & polish:** friends + one-off expenses, comments,
  notifications (in-app), dashboard, PWA manifest + service worker,
  responsive pass at mobile/desktop viewports.
- **Phase 4 (later, needs infra/keys):** Web Push (VAPID — open standard),
  email behind an `EmailProvider` interface (Nodemailer/SMTP; any provider
  is config, not code), cron reminders/digest via system cron on the host,
  realtime via Connect server-streaming/SSE from our own server. No
  Supabase, no Resend SDK, no Vercel.

## 7b. Deployment (self-hosted Docker)

- `Dockerfile` (repo root): multi-stage — pnpm install → `buf generate` →
  `next build` with `output: "standalone"` → slim runtime image running
  `node apps/web/server.js`. No native modules (pg is pure JS).
- `docker-compose.yml` (repo root): `db` (postgres:17-alpine, named volume,
  healthcheck) + `web` (built image, `DATABASE_URL` pointing at `db`,
  port 3000). Secrets come from the host `.env` (see `.env.example`).
- Local dev: `docker compose up -d db` then `pnpm dev` — or point
  `DATABASE_URL` at any Postgres you already run. Pending migrations from
  `apps/web/migrations/` apply automatically on boot; the runtime image
  ships the migrations folder so containers self-migrate on start.
- TLS/domain: any reverse proxy on the host (Caddy/nginx/Traefik) — out of
  scope for this repo.

## 8. Verification

- vitest unit tests: every split type reconciles to the exact total
  (rounding property cases), pairwise balances, simplify-debts.
- `buf lint` + generated code compiles; `tsc --noEmit`; ESLint clean;
  react-doctor scan.
- End-to-end: scripted Connect JSON calls (signup → group → expenses of each
  type → balances → settle → assert zeroed) against a running dev server.
- Manual responsive check at mobile + desktop viewports.

## 9. Native mobile app (v4 — 2026-07-13)

React Native app under `apps/mobile` (`@haalkhata/mobile`), reusing the
existing contract and backend unchanged — the "future native app" leg of the
architecture diagram, realized with React Native instead of Swift/Kotlin so
the generated TypeScript in `packages/protogen` is shared as-is.

**Decisions:**
- **Expo (managed) + expo-router.** File-based routing mirrors the web's
  App Router structure one-to-one; TypeScript throughout; Metro configured
  for the pnpm monorepo (workspace root watchFolders).
- **Same contract, same transport.** `@connectrpc/connect-web`'s Connect
  transport over JSON against `<server>/api/connect` — identical RPCs the
  browser calls. `TextEncoder`/`TextDecoder` polyfilled at the entry point.
  The API base URL comes from `EXPO_PUBLIC_API_URL`, falling back in dev to
  the Metro host (so a device on the LAN reaches the dev server).
- **Bearer-token auth.** LogIn/SignUp already return a token for mobile
  clients; it is kept in `expo-secure-store`, attached via a transport
  interceptor (`Authorization: Bearer`), and cleared on `unauthenticated`
  errors. The CSRF guard exempts bearer clients — no cookies involved.
- **Same data layer.** TanStack Query with the shared query-key registry
  and money-mutation invalidation set; cache persisted to AsyncStorage
  (parity with the web's localStorage persistence, offline-first startup).
- **Same structure conventions.** Route files in `app/` are thin
  orchestrators (the `page.tsx` role); each screen lives in
  `src/screens/<route>/components/<XScreen>/` with `hooks/` (useXAPI =
  all React Query calls, composed by useX), route-scoped `constants/` and
  pure `utils/` — the exact per-route pattern from §3. Shared UI in
  `src/components/ui|modals|providers`, client libs in `src/lib/api|money|theme`.
- **Same design language.** The "fresh ledger" tokens from globals.css
  (paper/card/ink/line, vermillion brand, pos/neg money semantics) live in
  `src/lib/theme/theme.ts`; StyleSheet-based styling, serif display type,
  lucide-react-native icons (same icon set as web).

```
apps/mobile/
  app/                        expo-router routes — THIN (mirror of page.tsx)
    _layout.tsx               providers + root stack
    login.tsx                 public auth screen
    (app)/_layout.tsx         session gate + authed stack
    (app)/(tabs)/_layout.tsx  bottom tabs: Home·Groups·Add·Scan·Friends
    (app)/(tabs)/<tab>.tsx    dashboard | groups | scan | friends | activity
    (app)/groups/[id].tsx     pushed detail screens
    (app)/expenses/new.tsx    (+ [id].tsx), account.tsx
  src/
    screens/<route>/          per-route fan-out (components/hooks/constants/utils)
    components/ui|modals|providers
    lib/api/                  connect.ts (transport+clients), session.ts, queryKeys.ts
    lib/money/ lib/theme/
```

**Feature parity v1:** login/signup, dashboard (summary, people, recent
activity, settle-up), groups (list/create/detail/invite/balances/simplify),
expenses (all non-itemized split types, multi-payer, edit, delete,
comments), friends (add/one-off/settle), activity feed with notification
badge + mark-read, account (profile, currency, sign out), receipt scan
(camera or library → AI draft → assign → save itemized).

**Verification:** `pnpm --filter @haalkhata/mobile typecheck | lint | test`
(vitest on pure utils); manual run via `pnpm dev:mobile` (Expo Go) against
the local dev server.
