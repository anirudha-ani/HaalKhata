# HaalKhata — Splitwise Clone: Architecture Plan (v4)

## Context

Greenfield build. Goal: a fully web-hosted Splitwise clone — responsive on
mobile and desktop browsers — with an AI feature that turns an uploaded
receipt photo into itemized line items (with tax + tip) that can be assigned
to people. Supports one-off spending and groups (trips, home, etc.), all core
Splitwise features, and a clean schema-first API contract so a native mobile
app can reuse the backend later. Direct payment settlement is deferred;
recording settlements is in.

**Decisions locked with the user (v3 — supersedes v2):**
- **No vendor lock-in, full control (v3).** Deploy target is a self-hosted
  Docker host (any VPS), NOT Vercel. Managed services are allowed only
  behind swappable interfaces or a plain connection string.
- **Database: Postgres from day one (v3 — replaces SQLite).** No SQLite
  anywhere. Local dev and prod both run vanilla Postgres (dev via
  `docker compose up db` or any local Postgres; prod via the compose file).
  The repo layer stays the only place SQL lives; the driver is `pg`
  (node-postgres), no ORM.
- **Schema as versioned SQL migrations (v3.1).** The schema is defined in
  plain `.sql` files under `apps/web/migrations/` run by node-pg-migrate
  (history table `pgmigrations`). Pending migrations auto-apply once per
  process on boot (db.ts), so dev and Docker stay zero-step; the CLI
  (`pnpm db:new`, `pnpm db:migrate`) is for authoring and applying migrations.
  Populated databases move forward only; recovery uses a verified backup or a
  new corrective migration. No inline DDL in code.
- **Backend: Node/TypeScript inside Next.js** (no Go, no Fly.io). One
  language, one deploy artifact (Next standalone output in Docker).
- **API contract: ConnectRPC + Protobuf stays.** `.proto` files remain the
  single source of truth; `buf` + `protoc-gen-es` generate the TypeScript
  messages and service descriptors used by BOTH the server handlers and the
  web client. A future mobile app regenerates a Swift/Kotlin client from the
  identical protos and calls the same `/api/connect/*` endpoints — one
  contract, no drift, no rewrite.
- **Storage:** repository layer (`/repo`) owns ALL SQL — Postgres via `pg`,
  async throughout. Because no SQL leaks outside `/repo`, changing hosts is
  a `DATABASE_URL` change; there is nothing provider-specific to migrate.
- **Auth:** email *or phone* + password with signed bearer tokens (see §4b).
  Login RPC sets an httpOnly cookie (web) and returns the token in the
  response body (mobile). Every RPC accepts either the cookie or
  `Authorization: Bearer`.
- **AI receipt parsing: no vendor lock.** Provider abstraction with
  config-driven ordering, plus a mock provider so the flow always works
  without keys. Superseded by §6b — the deploy target has no GPU, so the
  single real provider is an OpenAI-compatible endpoint pointed at OpenRouter
  under a zero-data-retention policy, and the per-vendor SDKs are gone.
- **Notifications:** in-app notifications now; Web Push (VAPID) + email
  (Resend) are a later phase (need keys/infra).

## Goal / Deliverable

A working app where a real user can: sign up / log in, create groups and add
members by email (even before they sign up — "shadow users" claim their
account at signup), add expenses with any split type (equal, exact amounts,
percentages, shares, itemized), record multiple payers, scan a receipt photo
into an editable itemized draft and tap-assign items to people (tax + tip
split proportionally), see who owes whom per group and overall, simplify
debts (min cash flow), record settlements, comment on expenses, see an
activity feed and in-app notifications — responsive on mobile + desktop,
installable PWA shell.

Explicitly NOT in v1: payment rails, FX conversion, native mobile app
(contract-ready only), SMS, Web Push/email delivery.

## 1. Architecture Overview

```
Browser (mobile + desktop)                       future native app
   │  typed Connect client (gen TS)                 │  generated Swift/Kotlin client
   ▼                                                ▼
/api/connect/*  ── ConnectRPC over HTTP (JSON/binary) ── one contract from /proto
   │
   ▼
apps/web/src/server/api/connect/   handlers: transport concerns ONLY
   │                               (decode, auth context, map errors)
   ▼
apps/web/src/server/usecase/       ALL business logic (split math, balances,
   │                               debt simplification, validation, activity)
   ▼
apps/web/src/server/repo/          ALL SQL (Postgres via pg)
```

Layering rules (enforced by review):
- `api/connect` handlers: no SQL, no business logic. Decode request → call
  usecase → encode response. `routes.ts` wires services to the router.
- `usecase`: pure TypeScript business logic. No SQL, no transport types
  beyond the generated proto messages. Domain math (splits, balances,
  simplify) lives in `usecase/domain/` (balances) and
  `@haalkhata/shared/expense/` (splits) as pure functions — unit tested.
- `repo`: SQL only. No business decisions.

## 2b. Shared client package (v5 — 2026-07-26)

`apps/web` and `apps/mobile` are both TypeScript clients of the same contract,
so a class of client-side code is genuinely common to them: the React Query key
registry, the cents-based money helpers, and the greeting helper. These were
originally duplicated file-for-file, kept in sync by an AGENTS.md instruction
telling humans to keep them byte-identical. Nothing enforced it, and silent
drift in `queryKeys.ts` produces stale-cache bugs that are near-impossible to
reproduce.

**Decision:** the duplicated files move to `packages/shared`
(`@haalkhata/shared`), a hand-written workspace package consumed by both apps —
converting a discipline problem into a compiler problem.

```
/packages/shared/
  src/api/queryKeys.ts         query-key registry + MONEY_KEYS invalidation set
  src/money/money.ts           formatMoney / parseMoneyInput / centsToInput / todayISO
  src/money/money.constants.ts CURRENCIES, CATEGORIES
  src/money/money.test.ts      colocated unit tests (vitest)
  src/expense/allocate.ts      allocate() — largest-remainder cent allocation
  src/expense/splits.ts        computeSplits / computeItemizedSplits (+ tests)
  src/search/filter.ts         searchTerms / matchesTerms (+ tests)
  src/greeting.ts              time-of-day greeting
```

**Amendment (v5.1 — 2026-07-26):** the split math moved here from
`apps/web/src/server/expense/domain/`. It is the one exception to "client
code": the SERVER usecase imports it too. The reason is the itemized editor
(§3b) — it shows a live per-person total as you fill the grid, and that figure
has to be the figure that gets saved. Re-implementing largest-remainder
allocation in the client would put cent-exact money logic in two places, which
is exactly the drift this package exists to prevent. Balance math
(`pairwiseBalances`, `simplifyDebts`) stays in `server/expense/domain/` — the
client has no use for it.

- Consumed as `@haalkhata/shared/<subpath>` (subpath exports mapping straight
  to `./src/*.ts`, exactly like `@haalkhata/protogen`). Raw TypeScript, no
  build step — Next transpiles it via `transpilePackages`, Metro via the
  existing workspace `watchFolders`.
- **Admission rule:** only code that is (a) pure TypeScript, (b) free of React,
  React Native, DOM and Node APIs, and (c) actually needed by both apps. UI
  primitives stay per-app (they render to different renderers); the Connect
  transports stay per-app (cookie auth vs bearer auth).
- Its own quality gates (`typecheck` / `lint` / `test`) run from the root
  alongside the app gates, so the shared code is held to the same
  id-length + JSDoc conventions as everything else.

## 3. Frontend structure (per route)

```
src/app/<route>/
├── page.tsx                  # THIN orchestrator: params, providers, render
├── loading.tsx               # Route-level loading UI
├── types/ constants/ hooks/ utils/   # Route-scoped; tests colocated in utils/
└── components/
    └── <PageComponent>/
        ├── <PageComponent>.tsx   # component orchestrator: ONE composite hook,
        │                         # assembles sub-trees, owns fallbacks
        ├── hooks/                # useXAPI (all React Query calls), useXState,
        │                         # useXHandlers, composed by useX
        ├── utils/                # pure helpers
        └── components/           # sub-components repeating this structure
```

- Data: TanStack Query wrapping the typed Connect client (`useXAPI` hooks own
  every query/mutation; components never call the client directly).
- Tooling: ESLint (flat config + next + typescript rules), react-doctor scan,
  vitest for domain/unit tests, `buf lint` + `buf breaking` for the contract.
- Naming/docs (mandated 2026-07-12): every identifier ≥ 4 characters, no
  abbreviations (enforced by eslint `id-length`; DB-column/proto property
  names exempt); every file has a header doc comment; every exported symbol
  and non-trivial internal function carries JSDoc (@param/@returns).
- Constants (mandated 2026-07-12): never inline between functions. Server:
  one `<domain>.constants.ts` per domain (auth, group, expense, receipt,
  common/db, api/connect). Frontend: route-scoped constants in the route's
  `constants/` folder; shared constants in the owning folder's
  `*.constants.ts` (e.g. components/ui/ui.constants.ts, lib/money/money.constants.ts).
  Live objects (handlers, provider impls, clients) are not constants and
  stay where they are.

## 3b. Itemized split editor (v5.1 — 2026-07-26)

Until now `split_type=itemized` could only be produced by the receipt scanner:
the expense form offered equal/exact/percent/shares, and the line-item editor
lived behind a photo upload on /scan. Splitting a bill by item without
photographing a receipt was impossible. The form now has a fifth **Itemized**
tab (`app/(app)/expenses/new/.../ItemizedEditor/`).

**Shape: a grid, items × people.** Rows are line items (name + amount),
columns are the people in the context, and a cell is that person's share of
that item. Tax and Tip are rows in the same grid; a totals row runs along the
bottom. This mirrors the one itemized UI its users call "nearly ideal" —
Splitwise's web view — whose praised properties are tabular entry, single-screen
person assignment, editable items, and tips as percentages.

**Interaction decisions, from UX research on bill splitters:**
- **New items arrive shared by everyone.** Splitting across the whole table is
  the common case, so it costs zero taps and the user only touches exceptions.
  Starting from an empty grid made a 10-item / 4-person bill cost ~40 taps.
- **Cells are toggles, not inputs.** The binding constraint is cognitive load
  (a receipt has 12–20 lines; working memory holds ~7), so the default mode is
  tap-to-include, never type-a-number.
- **Uneven shares are a mode, not the default.** A checkbox swaps the cells to
  integer weight inputs for "she had two, he had one". Weights are the existing
  `expense_item_assignments.weight` column — no schema change.
- **Live per-person totals.** The bottom row shows what each person currently
  owes, recomputed on every keystroke via the shared `computeItemizedSplits`
  (§2b amendment) — the preview is the saved figure, not an approximation.
- **Tip presets** (10/15/18/20% of the items subtotal) alongside the raw input.

The Amount field at the top of the form becomes a read-only readout of
items + tax + tip while this tab is active; the server independently recomputes
that sum and rejects a mismatch.

Editing an existing itemized expense is still blocked (unchanged) — the guard
in NewExpensePage stands until the editor can round-trip saved items.

## 3c. Ad-hoc participants: "who's on this?" (v5.6 — 2026-07-26)

The expense form and /scan both asked "Who is this with?" through a single
`<select>` whose value was `g:<groupId>` or `f:<friendId>`. That made the cast
of an expense **exactly one group or exactly one friend** — a dinner with three
friends could not be entered at all without first creating a group. The server
never had this limitation: `expenses.group_id` is nullable, `expense_splits` /
`expense_payers` take any number of rows, and createExpense already
auto-friends every participant of a one-off (§ expense.usecase). It was purely
a client-side constraint.

**How Splitwise models this** (researched 2026-07-26): the add-a-bill form has
a token field labelled "With you and:" holding one chip per person, plus a
group line that reads "No group" by default. Picking a group inserts it as a
token; to make a one-off you *delete the group token and type names instead*.
So group and ad-hoc cast are alternatives, not layers — which is also what our
server enforces (a group expense validates that every participant is a member).

**Our shape** — `components/people/PeoplePicker.tsx`, used by both routes:

  Who's on this?
  [You] [Sarah ×] [Mike ×]            ← chips; you are pinned, others removable
  [ Add people ▾ ]                    ← disclosure over a searchable checkbox list
  Group  [ No group ▾ ]               ← separate select; picking one takes over

- **Chips, not a multi-select.** Selected people stay visible as removable
  chips; the candidate list is a plain `<fieldset>` of checkboxes in a scroll
  container with a filter box, per Roselli's "Under-Engineered Multi-Selects" —
  no custom combobox, no ARIA to get wrong, and `<select multiple>` avoided
  because it tests badly and hides the current selection.
- **Group and people are exclusive.** Choosing a group replaces the cast with
  its members (chips render non-removable, the Add-people disclosure hides);
  choosing "No group" clears back to just you. This matches the server rule and
  Splitwise's delete-the-token flow, and avoids Splitwise's own worst behaviour
  — adding a non-member to a group bill silently splits it into two expenses.
- **Filter appears only past 6 friends**; below that the list is short enough
  to scan.

**State**: `context: string` is replaced by `groupId: string` (""= none) and
`friendIds: string[]` (ordered ad-hoc extras). `people` derives from whichever
is set, always with the signed-in user first, resolved through a directory
built from friends ∪ group members ∪ the edited expense's `users` — so a
participant who is not in the friends list still renders.

**Pruning is the correctness-critical part.** Removing a person must not leave
them in the request: `submit` sends `payerAmounts` unfiltered and
`buildItemsPayload` reads `items[].assignees` unfiltered, so a stale key would
have been posted as a payer or an item assignment. Dropping a chip therefore
prunes `checked`, `splitInputs`, `payerAmounts` and every item's `assignees`,
and resets `singlePayerId` to you when the removed person was the payer.

**Mobile** carries the same model through its four touchpoints (expense form
and scan screen, hook + screen each). It has no room for a disclosure panel, so
it keeps its existing `Chip` rows: the friends row becomes multi-select, the
groups row stays single-select and re-tapping the selected group clears it.

**Side effect: editing a one-off expense is fixed.** `buildInitialValues`
previously mapped a non-group expense to `context: ""`, so the edit form loaded
with a cast of just you and would have re-saved the expense as a solo one.
Participants are now recovered from the expense's splits and payers.

## 3d. Search and filtering (v5.7 — 2026-07-26)

The participant picker (§3c) shipped with its filter box gated behind 6+
friends, which is fine at 3 friends and unusable at 300. UX research settles
the threshold question: Material draws the dropdown line at 6 options and
Carbon at 3, but past roughly **15 options** the scan-and-scroll cost is high
enough that a filterable text field is the right control, and for hundreds the
guidance is search plus recency-ordered defaults plus paging rather than one
long list.

Shared pieces:
- `components/ui/SearchField.tsx` — icon, `type="search"`, clear button.
- `@haalkhata/shared/search/filter` — `searchTerms` + `matchesTerms`:
  whitespace-tokenised, order-independent, so "test ani" finds "Ani Test" where
  a substring match on the joined string would not. An all-digits term is
  matched against the fields' digits, so "415 555" finds "+1 (415) 555-2671"
  however punctuated. (Started in `apps/web/src/lib/search/`; moved to the
  shared package in §3i when the mobile member picker needed the same rules.)
  Unit-tested in `filter.test.ts`.

Applied at:
- **Add expense / scan picker** — search always present (name, email, phone),
  at most `MAX_VISIBLE_FRIENDS` rows rendered with a "showing N of M" count,
  autofocus only when the user opens the panel themselves (never on page load,
  which would pop the mobile keyboard). Ordering is left exactly as
  `listFriends` returns it — counterparties first, then alphabetical — which is
  already the recency signal the research asks for, so no re-ranking.
- **Friends** — name / email / phone, with a match count.
- **Groups** — name and type, so "trip" pulls up every trip.
- **Activity** — free text over the pre-rendered message and actor, plus
  All / Expenses / Payments / Comments / Groups type buttons. The active button
  is styled and a count shows when rows are hidden, since a filter that changes
  what you see has to say so.

## 3e. One grid for both bills; receipt shown beside it (v5.8 — 2026-07-26)

/scan and the expense form's Itemized tab had drifted into two different UIs
for the same job: the form had the items × people grid (§3b), while /scan still
used per-item avatar chip rows with no uneven shares, no tip presets, no live
per-person totals, and a single payer. Three changes close the gap.

**One grid.** `components/expense/ItemGrid.tsx` is now the single implementation,
driven by explicit props rather than a form controller, and used by both. It
gains an optional leading **Qty** column (only /scan reads a quantity off the
bill), so `DraftLineItem.quantity` is optional and `buildItemsPayload` saves
`quantity ?? 1`. `ItemizedEditor` is a thin adapter over it. Because /scan now
shares the draft type it also inherits `checkItemized`, `previewItemizedShares`
and `checkPayers` — so its totals row runs the server's own allocator. Those
helpers moved from `app/(app)/expenses/new/utils/splitForm.ts` to
`lib/expense/splitForm.ts`: two routes need them, so they no longer live inside
one route.

Parsed rows now arrive **shared by everyone**, matching the grid's stated
default, instead of every item starting unassigned. The mirror rule follows:
adding a person to a scanned receipt puts them on every line, and you untick
their exceptions.

**Tax and tip show their rate** (v5.15 — 2026-07-27). A bare "7.26" says
nothing about whether it is the tax you expected, so each add-on now reads out
as a percentage beside its amount — "8.6% of items". The base is the pre-tax
subtotal, which is both how a real bill reckons them and the base
`applyTipPercent` already used: measuring against the grand total instead
would make tapping the 18% preset read back as 15.3%, so the control and the
readout would contradict each other on screen. `percentOfItems` is a pure
helper in `lib/expense/splitForm.ts`; it shows nothing for a zero or absent
amount rather than "0%", and does not clamp — a tax fat-fingered to ten times
the bill reads "1000%", which is the point.

**The receipt sits next to the draft.** `ParseReceiptResponse` gained
`bytes normalized_image` — the exact JPEG the provider was shown, i.e. the
upload after EXIF rotation, downscaling and HEIC transcoding. Two reasons it
has to come from the server rather than the local file: browsers cannot decode
HEIC at all, so an iPhone receipt was previously unviewable; and this is the
image the numbers were actually read from, which is the thing worth checking
against. It is ~900 KB for a phone photo, never stored, and only round-trips to
the person who uploaded it. Past `lg:` the page becomes two columns with the
photo sticky, so it stays beside the grid all the way down.

**Multiple payers.** /scan gets the expense form's payer editor — a "multiple
people paid" toggle over per-person amount inputs, validated by the same
`checkPayers`. Verified live end to end: HEIC → 923 KB JPEG → Zazie, 2 items →
saved itemized, total 4345, payers 1448+2897, splits 1448/1448/1449.

Mobile still has its own chip-based scan draft; it is unchanged and unaffected
(the proto field is additive).

## 3f. Friends as a ledger, not a list (v5.9 — 2026-07-26)

The Friends tab showed a name, a net figure and a "+" — and nothing else. Two
things were missing outright, both fatal in a ledger app:

- **You could not settle when someone owed you.** `RecordSettlement` only ever
  recorded caller → recipient, and the Settle button only rendered when
  `netCents < 0`. With every friend owing you, the page had no settle action at
  all. Recording "they paid me back" was impossible through any surface.
- **There was no way to see the history with a person.** No route, no query —
  just a total with nothing behind it. `listOneOffExpensesBetween` existed but
  covered only non-group expenses and was never wired to a screen.

**What a friend screen has to do** (Splitwise's own design, plus the ledger /
statement conventions those apps inherit from accounting):
1. Balance across *everything* shared, group expenses included — Splitwise's
   friend screen totals across all groups, and settling the full amount settles
   each group behind it.
2. Every entry in one chronological list with a **running balance**: opening
   position, each line's effect, closing position. This is the ledger
   convention (statement with per-row running balance) and it is what makes a
   disputed total checkable line by line.
3. Each line says which direction it moved the balance and by how much — the
   expense total alone is not enough, because your share of it is what counts.
4. Settle in either direction, one action, prominent.
5. Settled up is an affirmation, not an empty list. Splitwise shows a check
   mark rather than a blank sheet, with the history still one click away.

**Server.** New `GetFriendLedger` RPC on ExpenseService returning the friend,
the net, per-group balances, and the merged entry list. A new repo query
`listExpensesBetween` is `listOneOffExpensesBetween` without the
`group_id IS NULL` clause, so shared group expenses count. Each entry's
`delta_cents` comes from `expenseDebts` — the same per-expense pairwise
attribution the balances already use — so the running balance lands exactly on
the net that `getOverallBalances` reports rather than a second, subtly
different number. Settlements between the two of you are folded into the same
list.

`RecordSettlementRequest` gains `bool received` (false = you paid them, the
existing behaviour). When true the settlement is stored friend → you, and the
"you cannot settle more than you owe" guard is checked in that direction
instead — the guard exists so a settlement cannot flip a balance in your
favour, and that reasoning holds symmetrically.

**Client.** `/friends/[id]` is the new detail screen: balance headline, Settle
up / Add expense actions, per-group breakdown when the friendship spans groups,
and the running-balance ledger. The list page gets a totals header (owed to you
/ you owe), rows that are links, and a settle action in both directions.

## 3g. Settling: US rails, payment handles, reminders (v5.10 — 2026-07-26)

`bkash` was still in the settlement methods — another leftover from the
Bangladesh assumption §4b already cleared out of the identifiers. Methods are
now `venmo | zelle | cashapp | paypal | cash | bank | other`, defined once in
`packages/shared/src/payment/methods.ts` and imported by both the client
picker and the server's validation set, so the two cannot drift.

**Payment handles.** New `payment_handles(user_id, method, handle)` table —
a table rather than columns on `users` because the set of P2P apps changes and
adding one should be a constant, not a migration. Handles are stored verbatim:
a $cashtag or Venmo username is an opaque identifier, not an address to
normalize. They are attached in `users.repo`'s own lookups via a `USER_COLUMNS`
fragment, not fetched separately, because the settle modal is reached from four
screens with four different sources for the recipient and any one of them would
otherwise silently lack them.

**What each app can actually be handed** is modelled, not guessed:
- Venmo — `venmo.com/<user>?txn=pay&amount=&note=`, amount and note prefill.
- PayPal — `paypal.me/<name>/<amount>`, amount prefills.
- Cash App — `cash.app/$<cashtag>`; **cannot** carry an amount, and the UI says so.
- Zelle — no universal link exists (it lives inside each bank's app), so the
  affordance is copy-the-handle and the UI says that too.
Only https URLs are produced, never `venmo://` — a custom scheme shows a
browser error when the app is missing, whereas the web URL redirects into the
app when present and works without it.

**The settle modal** leads with who pays whom and the outstanding amount, then
the method picker (a dot marks the apps this person can actually be paid on),
then the recipient's handle in a copy block with an Open button. It states
plainly that recording a payment does not move money — this is a ledger, not a
payment processor.

The handle block appears **only when you are the one paying**. A first cut
showed the payee's handle in both directions, reasoning that "record a payment
received" should surface your own — which was wrong twice over: the money has
already arrived so there is nobody to send anything to, and the Open button it
produced pointed at `venmo.com/<you>?txn=pay`, i.e. pay yourself. Received mode
now shows amount, method and note only, and says it is logging money already
sent rather than telling you to move any.

Telling somebody where to send money is the **reminder's** job instead: the
notification carries the sender's handles, so the person who owes gets the
Venmo username in the nudge itself rather than having to ask.

**Reminders.** `SendReminder` posts an in-app notification to someone who owes
you. Two guards, both server-side because the sender is not the party who
suffers when they are missing: the debt must currently exist, and the same
person cannot be reminded twice within `REMINDER_COOLDOWN_HOURS` (24). The
previous reminder notification is its own cooldown record, so no extra table.

## 3h. Activity: paginated, filterable, legible (v5.11 — 2026-07-26)

The feed was a hard `LIMIT 50` with no cursor and no offset — event 51 was
permanently unreachable, and the page never said so. It also leaned entirely on
one pre-rendered message string per row, which is why the UI could not be
smart: it had no amount to right-align and no idea which direction money moved.

**Icons: three passes to get here.** The original emoji were wrong on the
merits — 💸 (money flying away) was drawn for being *paid*, i.e. the opposite
of what happened; flat 🧾 and 🗑️ at 20px are two grey smudges, so added and
deleted read identically; 📒 for a new group is a ledger binder nobody
associates with people.

Pass two replaced them with lucide icons: semantically right, visually
corporate. Pass three brought back the personality without the defects, as
**custom SVG** in `ActivityGlyph` — a receipt with a torn hem, a headstone for
a deleted expense, a cinched money bag for being paid, a paper plane for money
sent, a party popper for a new group, a squiggle-filled speech bubble, a
raised hand for someone joining.

Drawn rather than picked, for reasons that survive argument: emoji are
rendered by the OS, so the same feed looks like three different apps across
platforms and their baked-in colours fight the tile tint; a stock icon set is
consistent but characterless. These are stroked in `currentColor`, so the tile
decides the colour and one file serves every tint.

Two things the drawings must keep doing. Colour is never the only signal —
added (receipt, brand tint) and deleted (headstone, muted) differ by tint
*and* by drawing *and* by the amount's own sign. And each tile carries an
`aria-label` while the SVG is `aria-hidden`, so a screen reader announces
"Expense deleted" instead of describing a headstone.

The winged banknote is the outbound glyph, which is right: a winged note is
exactly what 💸 depicts, and the original defect was never the drawing — it was
showing it for money *received*, where it said the opposite of what happened.
With direction resolved per viewer it can only land on a payment you made.

It is a **coin**, not a banknote, and that was the fix. Roughly thirty rendered
variants of a winged note all failed for the same structural reason: a note is
a rectangle, and a rectangle with wings has no good answer at 24px. Wings above
its corners read as bunny ears; wings at its sides read as a bowtie; a diagonal
composition matching the emoji needs feather detail the size cannot hold, and
degrades into insect legs. A coin is a circle — the same base shape as every
other glyph in this set — so it sits in the column instead of fighting it, and
the winged-sphere silhouette (a golden snitch) is legible at any size because
the outline alone carries it. The coin stays large enough for its "$" to
survive, that sign being the only thing saying "money" on a neutral tile.

Two general lessons came out of the detour. **Judge a glyph beside its
neighbours, not alone** — solid wings read fine in isolation and looked like a
blob in the column, so the harness now renders a reference glyph alongside every
candidate. And **detail loses to size**: every other glyph here is one big
circle plus two or three marks, and anything busier reads as mush no matter how
correct it is up close.

No captions. An earlier pass put a quip under each row ("new damage", "secured
the bag"); it repeated what the sentence already said and pushed the timestamp
around for nothing. The metadata line is the actor and the time.

The harness renders at true size (40px tile) with a 3x row beside it. An
earlier pass previewed at 66px and shipped a tear fused to a face outline and
dollar signs the size of specks; at half the size, details that looked fine
simply stop existing. Shipped paths are checked byte-for-byte against the
previewed ones.

**Structured fields, additively.** activity gains `amount_cents`, `currency`
and `credit_user_id` (for a settlement, who received). ActivityEvent exposes
`amount_cents`, `currency` and `inbound`, the last computed per viewer, which
is what makes the settlement arrow point the right way. The pre-rendered
message stays — it is still the accessible sentence — but the amount is lifted
out of it and set right-aligned in tabular figures.

**Pagination: keyset, with a Load more button.** `(created_at, id)` descending
as the cursor, because OFFSET drifts when rows are inserted while you page.
Load more rather than infinite scroll — the research consensus is that infinite
scroll suits discovery feeds while an explicit control suits task-driven lists,
and a ledger you are auditing is the latter. `next_cursor` is empty when the
feed is exhausted.

**Month filter** built from `months`, the list of months that actually contain
activity, newest first — an open date picker would offer thousands of empty
months. Selecting one scopes both the query and the pagination.

**Date grouping** by Today / Yesterday / full date, so scanning is by when
rather than by row.

## 3i. Group membership: pick people, don't invite them (v5.12 — 2026-07-27)

Group membership was **email-only**. The one control on a group was "Invite",
and it opened a single email input — so putting three existing friends in a
trip meant typing three addresses you already had on file, one modal at a
time, and the group you had just created sat there with one member in it.
§4b already flagged this ("Group invites remain email-only for now — the same
treatment applies whenever that flow is revisited"). This is that revisit.

Every other app in this space treats an email invite as the **fallback**, not
the primary path: you pick from the people you already know, and typing an
address is what you do for the one person who is new. The picker for that
already exists here — `PeoplePicker` on the expense form — so the fix is
mostly to stop having two answers to "who are these people?".

**Contract.** `AddMember(email)` → `AddMembers`, batched:

```proto
rpc AddMembers(AddMembersRequest) returns (AddMembersResponse);
message AddMembersRequest {
  string group_id = 1;
  repeated string user_ids = 2;  // people you already know — added outright
  string email = 3;              // \  the one newcomer, exactly one of the
  string phone = 4;              // /  two, following §4b's identifier split
  string name = 5;               // optional display name for a shadow user
}
message AddMembersResponse { repeated Member added = 1; }
```

`CreateGroupRequest` gains the same `repeated string member_ids`, so a group
is born populated rather than empty-then-invited.

**Who you are allowed to add.** A bare id is not authorization: without a
check, any user id would be enough to enrol a stranger in your group and start
attributing debts to them. The server admits an id only if it is in
`connectedUserIds(caller)` = explicit friendships ∪ **anyone you already share
a group with**. The second half is what keeps the guard aligned with what the
client actually offers: friendships are symmetric, but two people who met as
members of someone else's group have no friendship row between them, and
`listFriends` surfaces them anyway once they share an expense. Guarding on
friendship alone would show a name in the picker that the server then refuses.

**Who may add.** Any member, not just the owner. A group is a shared ledger,
and whoever notices somebody is missing from the dinner is rarely the person
who happened to create the group — routing every addition through one account
makes them a bottleneck for a change anyone present can see is correct.
`RemoveMember` is owner-only for removing *somebody else*: it is the
destructive direction, and it is already gated on the leaver's balance being
settled. A non-owner may remove *themselves* under the same zero-balance gate
(2026-08-29, security audit H1): membership is consensual only if the person a
co-member enrolled can walk out again. Both clients offer "Leave group" from
the members list, and the owner gets "Remove" on every other row there.

**Batch semantics.** Adding is idempotent per person: someone already in the
group is *skipped*, not an error, so one already-member cannot fail the other
four. The call fails only when nothing at all would happen — nobody picked, or
every person picked is already in. One `member_added` event is written for the
whole batch ("Ani added Rifat, Tanvir and Sadia"), not one per person, because
a feed that reports a single action three times is noise.

**UI.** "Invite" becomes **Add people**, and the modal is the same shape in
both places it appears (new-group form, group detail):

```
  Search  [ name                      ]      ← names only: others' email and
  ☑ Rifat        ☐ Tanvir       ☐ Sadia      ←   phone are private (2026-08-29)
  ── Not on the list? ─────────────────
  [ email or phone            ]  ← the fallback, below the fold
```

`FriendChecklist` (`components/people/`) is that middle block, extracted from
`PeoplePicker` so all three callers share one search, one 50-row cap, and one
overflow hint rather than three copies that drift.

**Revised 2026-08-29 (security audit H1/H2).** The fallback no longer creates
a shadow user. An email or phone must resolve to an existing account the
caller is already connected with — the same `connectedUserIds` rule as the
picked ids — and anything else is refused with the same generic denial, so
the field is not an account-existence oracle either. Somebody genuinely new
is brought in by a friend request (§3f) that they accept first. Both clients
say so under the field instead of promising a share "tracked and waiting when
they sign up".

## 3j. Scanning is not a kind of expense (v5.13 — 2026-07-27)

/scan and /expenses/new were separate destinations, each with its own nav
entry, its own route, its own controller and its own API hook. §3e had already
noticed they were converging and made them share `ItemGrid` — but sharing a
component while staying two pages left the split intact where it was most
visible: a group header carried **two buttons**, "Scan receipt" and "Add
expense", for what is one act with two ways of filling in the form.

Scanning a receipt is not a *kind* of expense. It is a faster way to populate
the same expense — the saved row is identical either way (`split_type =
itemized`, which the Itemized tab already produces by hand). So the receipt
becomes an input to the expense form rather than a parallel route.

**One page.** `/expenses/new` opens with a receipt dropzone above the form:

```
  [ 📷  Scan a receipt — items, tax and tip fill themselves in ]
  Who's on this?  ...
  What was it for?  ...
```

Picking a photo reveals "Itemize with AI"; parsing fills description (merchant),
date, tax, tip and the item rows, flips the split to **Itemized**, and turns
the page two-column past `lg:` with the photo sticky beside the grid. Every
control below is the form's own — `ItemizedEditor` and `PayerEditor`, not
copies of them. `DraftEditor` is deleted: it was the payer editor and the item
grid rebuilt against a second controller.

**Tap count is unchanged.** /scan also required tapping its upload zone, so
"Add expense → dropzone → camera" is exactly as many taps as "Scan → dropzone
→ camera" was. Nothing got slower; a destination got removed.

**Deletions.** `useScan`, `useScanAPI`, `ScanPage`, `DraftEditor`. The `parse`
mutation moves into `useNewExpenseAPI` — the rest of `useScanAPI` was already
a duplicate of it (same me/groups/friends, same create). `/scan` stays as a
redirect so existing links and bookmarks keep working, forwarding `?group` /
`?friend`.

**Nav.** The Scan entry is gone from the sidebar and the mobile bottom bar;
Activity takes the freed mobile slot, which keeps the 5-column grid at 2 +
add + 2 and stops Activity being reachable only via the header bell. The
"Scan receipt" buttons on group detail, friend detail and the dashboard
collapse into the "Add expense" they now duplicate.

**Mobile app unaffected.** apps/mobile keeps its own scan tab: its expense
form has no itemized editor at all (§3e), so folding scan into it there means
porting the item grid to React Native first. Tracked, not done here.

## 3k. Add expense on a phone (v5.16 — 2026-07-27)

The form was responsive in the sense that nothing overflowed, which is not the
same as usable. Adding an expense is overwhelmingly a phone job — you do it at
the table, with the receipt in your hand — so the phone is the primary target,
not the fallback.

**`capture` was hiding the photo library.** The single file input carried
`capture="environment"`, which on both iOS and Android opens the camera and
offers *no way to reach an existing photo*. That breaks the most common
sequence there is: photograph the receipt at dinner, split it later on the
train. There are now two controls — **Take photo** (`capture`, phone-only via
`sm:hidden`) and **Choose photo** (no `capture`, everywhere). The `accept`
list carries bare extensions alongside MIME types because iOS reports a
library HEIC with an empty type, which a MIME-only list greys out — the one
format an iPhone shoots by default becoming the one you cannot pick.

**Uploads shrink before they leave the phone.** A phone shot is 3–12 MB, all
of which crossed a mobile connection so the server could downsample it to
2576px anyway — and anything over 8 MB was rejected *after* the wait.
`lib/image/receiptImage.ts` redraws to the same 2576px ceiling and re-encodes
at JPEG 0.85, typically a few hundred KB. Every failure path returns the
original file rather than throwing: HEIC (no browser decodes it), no
`createImageBitmap`, no canvas, or a re-encode that came out larger. A photo
that uploads slowly still works; one that never uploads does not. EXIF
rotation is baked in via `imageOrientation: "from-image"`, making the server's
own rotate a no-op. `isPreparing` covers the decode, which is a visible pause
on a 12-megapixel image and would otherwise read as a dead tap.

**iOS zoom.** Any focused input under 16px makes Safari zoom the whole page,
and the grid's inputs inherited the table's `text-sm` (14px). The zoom then
strands you scrolled sideways inside a horizontally-scrolling table with no
obvious way back. Grid cells, the search field and the notes box are
`text-base` on phones and `sm:text-sm` from the breakpoint up, where no such
rule exists.

**The item column is pinned.** With four people the grid is wider than a
phone, and reaching someone's column used to carry the item name off screen —
you were ticking a checkbox with no idea which line it belonged to.
`sticky left-0` holds the name, Tax, Tip and Total labels in place. Pinned
cells must be opaque, so the unassigned-row tint went from `bg-neg-50/40` to
solid: a translucent row beside an opaque cell renders as two colours.

**Tap targets** go to 40px on phones (`h-10 sm:h-8`) for the assignee toggles,
amount and quantity cells, and 48px (`min-h-12`) on the primary buttons.
Category chips scroll horizontally instead of wrapping — eleven of them wrap
to three rows, pushing the split editor, the thing you came for, below the
fold. The five split tabs drop to `text-xs` on phones, where `text-sm` overran
a 375px screen.

**Verification.** No browser is installed on this box, so the layout is not
visually confirmed — stated plainly rather than implied. What *is* checked:
the pure resize logic has unit tests (12), and compiling Tailwind against the
real sources confirms all 19 new utilities actually generate. That last one
matters because a mistyped Tailwind class is not an error, it is silence.

## 3l. Secure-context APIs, and a phone on plain http (v5.17 — 2026-07-27)

Reported from mobile Safari: building an itemized bill from a photo died with
"crypto.randomUUID is not a function".

**The cause is the URL, not the browser.** `crypto.randomUUID` belongs to Web
Crypto, which browsers expose only in a **secure context**. `localhost` is
treated as one; `http://192.168.x.x:3000` — how you reach a dev server from a
phone on the same wifi — is not. So `crypto` exists and `randomUUID` does not,
and the itemized editor threw the moment it built a row. It never appeared on
a desktop because a desktop hits localhost.

**Fixed by not needing it.** `DraftLineItem.key` is documented "not sent to
the server" and `buildItemsPayload` emits `id: ""` for every row, so the key
only has to be distinct among the rows of one draft in one session. A counter
does that. `nextDraftKey` moves to `@haalkhata/shared/expense/draftKey` —
mobile had already written the identical counter for its own reason (Hermes
has never implemented `randomUUID`), so the shared package now holds one
implementation and the comment explaining both engines.

**The same class of bug, one modal over.** `navigator.clipboard` is also
secure-context-only, so "copy their Venmo handle" — a phone action if ever
there was one — threw on the same URL. `lib/clipboard/copyText.ts` tries the
modern API and falls back to `document.execCommand("copy")` over an offscreen
textarea. It reports success, and the button only flips to "Copied" when the
copy actually happened; claiming success after a silent failure is worse than
saying nothing. (`serviceWorker` is also gated, but its registration was
already behind a feature check and a `.catch()`, so it just no-ops.)

**A rotation bug this pass was about to ship.** §3k's client-side resize used
`createImageBitmap(file, { imageOrientation: "from-image" })`, which Safari
only honours from **16.4**. On an older iPhone the option is ignored, and
because the canvas re-encode drops the EXIF block the server loses its chance
to rotate too — the receipt would have arrived sideways with nothing left to
say it was. `lib/image/exifOrientation.ts` now reads tag 0x0112 out of the
JPEG directly and applies the turn on the canvas, with `imageOrientation:
"none"` so a browser that *does* honour the tag cannot rotate it twice.
Fixtures are real JPEGs emitted by sharp rather than bytes hand-assembled to
match the parser, which would only prove the parser agrees with itself.

**Rule going forward:** anything gated on a secure context needs a fallback,
because the phone is tested over plain http and that is exactly where these
features are needed.

## 3m. The shell is a frame, not a page (v5.18 — 2026-07-27)

Reported: on a phone the header and bottom bar "jiggle" — drifting with
sideways scrolling and bouncing on vertical. Two separate causes, one fix.

**`sticky` only pins one axis.** The mobile header was `sticky top-0`, which
pins vertically and nothing else, so the moment anything made the document
scroll horizontally the header slid along with it. **`fixed` is re-laid-out**
against the visual viewport, which iOS changes continuously while it animates
the URL bar and during momentum scroll — so the bottom nav bounced. Both are
symptoms of the same thing: the bars were overlays on a scrolling document.

**They are now rows of a frame that does not scroll.** The shell is
`fixed inset-0 overflow-hidden`; the header and nav are ordinary `shrink-0`
flex children; `<main>` is the single `overflow-y-auto` element. An element
that is not inside the scrolling box cannot be moved by scrolling it — no
sticky, nothing to recompute per frame.

**Pinned, not sized — arrived at after two wrong turns.** The first attempt
gave the shell `h-dvh`, and the nav ended up *behind* iOS's address bar, which
lives at the bottom of the screen. The second used `h-svh`, and the bars went
back to scrolling entirely. Both failures share a cause: a viewport height
only holds the frame together while the unit resolves the way you expect, and
iOS reports these differently depending on whether it believes a scroll is
still coming — which is itself a function of whether the document can scroll.
Circular, and not something to reason your way through from a spec.

`position: fixed; inset: 0` sidesteps the question. It takes the shell out of
flow, so the document has **no in-flow content at all** — `Providers` renders
no wrapper and `RegisterServiceWorker` returns null, so `<body>` is left with
literally nothing to scroll. No viewport unit is involved. It also puts the
bottom bar exactly where Safari puts any fixed element: above the address bar
rather than under it — which is the behaviour the *original* fixed nav already
had. The original's problem was never its position, only that the visual
viewport kept moving beneath it; a document that cannot scroll never moves it.

Because nothing in the shell sets `transform`, `filter` or `backdrop-filter`
(the blur came off with this change), a fixed ancestor does not become a
containing block for fixed descendants, so `Modal` stays viewport-relative and
escapes `<main>`'s overflow clipping as before.

Details that make it hold:
- `min-h-0` on `<main>`. A flex child will not shrink below its content
  height without it, so the frame would grow and the document would scroll
  after all — the exact bug, reintroduced one level down.
- `overscroll-contain` on `<main>` plus `overscroll-behavior: none` on
  html/body: stops the rubber-band at the end of a list from handing the
  scroll to the document, and kills pull-to-refresh, both of which drag the
  whole frame.
- The scroller is full width with `max-w-6xl` on the content *inside* it, so
  the desktop scrollbar sits at the edge of the content area instead of
  floating mid-screen.
- `relative z-10` on the bars — not to overlay the scroller, which they no
  longer do, but because the add button is pulled 20px above the bar by
  `-mt-5` and must paint over whatever scrolls past.
- `bg-card/95 backdrop-blur` became solid `bg-card`. The translucency existed
  because the bars overlaid content; now that nothing passes beneath them it
  bought only a per-frame blur composite, which is itself a source of jank.

`pb-24` on main is gone — it existed solely to clear the fixed nav.

## 4b. Account identifiers: email OR phone (v5.2 — 2026-07-26)

An account is reachable by **email, phone, or both** — the original
email-only assumption is gone (migration `1784073600000_add_user_phone`).

- `users.email` is nullable, `users.phone` is E.164 with a partial unique
  index (`WHERE phone IS NOT NULL`, so multiple NULLs are fine), and a
  `chk_users_has_identifier` CHECK guarantees at least one is present.
- Phone is normalized with `libphonenumber-js` (`normalizePhone` in
  `auth.constants.ts`) and only ever stored in E.164, so lookups are exact.
- **US-first, not US-only.** `normalizePhone` passes
  `DEFAULT_PHONE_REGION = "US"`, so national formats — `(617) 555-1212`,
  `617-555-1212`, `6175551212` — resolve to +1. Any number written with an
  explicit `+<country>` is still honored, so international users are never
  blocked. Without that default argument libphonenumber-js accepts ONLY
  `+`-prefixed input and silently rejects every national format, which is how
  this shipped until 2026-07-26. Rejections now return `PHONE_FORMAT_HINT`,
  which names the accepted shapes instead of a bare "invalid".
- Auth RPCs take `email` and `phone` fields with exactly one populated; the
  account is looked up by whichever was supplied.
- **Shadow users may be phone-only.** Inviting someone by phone creates a
  claimable row with NULL email, claimed at signup by that phone the same way
  an email invite is (`findOrCreateUserByPhone`, mirroring the email path
  including its unique-violation retry).
- Clients present **one "email or phone" field**, not two. The raw string is
  routed by `splitIdentifier` (`@haalkhata/shared/auth/identifier.ts`): an `@`
  means email, anything else is sent as phone for the server to validate. It
  lives in the shared package because login, signup and friend-invite on both
  apps all need identical routing.

Group invites took this treatment in §3i: `AddMembers` accepts the same
`email`/`phone` pair, and it is now the fallback behind picking people you
already know rather than the only way in.

**Phone as a login identifier is superseded by §4c** (Google is the only way
in). Everything else here stands: phone still invites, still creates
claimable shadow rows, still finds people, and is still normalized to E.164
by `normalizePhone`. `splitIdentifier` survives for the invite flows and
drops out of login only.

## 4c. Google sign-in, onboarding, account merge (v5.14 — 2026-07-27)

Email + password is a burden nobody wants to carry for an expense splitter.
**Sign in with Google becomes the only way in.** §4b's identifier model is
narrowed accordingly: phone stops being an *authentication* identifier and
keeps its other two jobs — a field on your profile, and a way to invite or
find people.

**Why the ID-token flow, not OAuth redirect or an auth library.** The session
layer here is hand-rolled and already correct: HMAC bearer tokens with
`token_version` revocation, minted in Connect handlers, shared with the Expo
app over `Authorization: Bearer`, cookie for web. Auth.js / better-auth want
to own sessions, so adopting one means replacing working infrastructure to
add one button. The full OAuth authorization-code flow buys Google API
access tokens we have no use for, at the cost of a callback route outside
the Connect mount, `state` handling, and a client secret to store and
rotate. Google Identity Services hands the browser a signed **ID token**;
the server verifies it against Google's JWKS and issues the same token it
already issues. **No client secret is involved and none should be
deployed** — only `GOOGLE_CLIENT_ID` (server, as the audience) and
`NEXT_PUBLIC_GOOGLE_CLIENT_ID` (browser).

Verification uses `google-auth-library` rather than hand-rolled JWT checks.
This is the one place not to write our own crypto: a missed `aud` check
means any Google app's token logs into ours.

**Publishing.** Only non-sensitive scopes (`openid`, `email`, `profile`) are
requested, so the OAuth client publishes to production with one button and
no Google review — verification exists for sensitive/restricted scopes
(Gmail, Drive, Calendar contents), which this never touches. Testing mode
caps at 100 listed test users, so publishing is required before real use.
A custom consent-screen logo is a separate brand review; skip it.

**Contract.**

```proto
rpc LogInWithGoogle(LogInWithGoogleRequest) returns (AuthResponse);
message LogInWithGoogleRequest { string id_token = 1; }
```

`SignUpRequest` / `LogInRequest` keep their `phone` fields — removing them
is a breaking change for any shipped mobile build, and an unused proto field
costs nothing.

**Password auth is kept in development and closed in production.** Seeded
dev accounts stay reachable without a Google round trip, while a real deploy
admits Google only. Two halves, and only one of them matters:

- `passwordAuthEnabled()` in `auth.constants.ts` gates `signUp` and `logIn`
  in the **usecase**, before any lookup. This is the enforcing side: the RPCs
  stay mounted and reachable by anyone willing to POST at them, so a hidden
  form on its own would be decoration.
- `PASSWORD_AUTH_ENABLED` in the login route's constants hides the form.
  Duplicated rather than imported because the server module reaches for
  `node:path` and cannot enter a client bundle. Since it resolves to a
  literal at build time, the whole block is dead-code eliminated from a
  production bundle — verified by grepping the built chunks for its strings.

Consequence for `apps/mobile`, which still signs in with a password: its
login breaks against a production server until it gets the Google flow. Not
an issue while the app is unreleased, but it is the reason mobile Google
sign-in cannot lag indefinitely.

**Schema.** `users.google_sub TEXT` with a partial unique index
(`WHERE google_sub IS NOT NULL`), plus `users.merged_into TEXT` for merge
tombstones. `password_hash` stays nullable and `chk_users_has_identifier` is
satisfied by the email, so nothing else moves.

**`registered` no longer means "has a password."** `toUser` derives it from
`password_hash !== null`, which reads every Google-only account as an
unclaimed shadow user. It becomes
`password_hash !== null || google_sub !== null`, and `signUp`'s
already-exists check widens the same way — otherwise someone who signed in
with Google can be "claimed" through the password signup form.

**Linking is only ever done on a verified email.** Google's `email_verified`
claim is checked before matching an existing row; matching on an unverified
address is account takeover, and Workspace-hosted domains are the case that
bites. A shadow row whose name was defaulted to the email's local part takes
Google's display name on link, but a name the person set themselves is never
overwritten.

### Onboarding (tranche 2)

A Google account arrives with no phone, so nobody can find its owner by
number — §4b's invite-by-phone path has nothing to match. A first-run flow
collects phone, default currency, and payment handles. This is nearly free
on the server: `UpdateProfile` already accepts everything except phone, so
onboarding is a first-run wrapper over an existing RPC reusing the account
page's components.

`users.onboarded_at TIMESTAMPTZ` gates it; the `(app)` layout redirects
while it is NULL. **Set it even when the user skips**, or the redirect is a
loop. Every field is skippable — a mandatory wizard reintroduces exactly the
friction that dropping passwords removed.

### Account merge (tranche 3)

Shadow rows are created by email **and** by phone (§4b), so one person can
accumulate two of them before they ever sign up. Google sign-in claims the
email one by verified-email match; the phone one is orphaned by
construction. Three cases:

- **Email shadow only** — matched at sign-in. Free, automatic, no merge.
- **Phone shadow only** — the signing-in row is empty, so absorbing is
  trivial.
- **Both** — a full history-to-history merge. No ordering trick avoids it;
  the person *becomes* the email row at sign-in, and that row already has
  history. This is the default outcome, not an edge case.

Adding a phone therefore resolves as: no holder → write; **unclaimed shadow
row → merge**; registered account → reject. Rejection applies only to
registered accounts, and its message must differ from the shadow case — "in
use by another account" is wrong and confusing when the row holding it is
the caller's own history.

**The merge is one transaction.** Repointing the 13 FK columns is the easy
half; the hazards are:

- `expense_splits` / `expense_payers` PK `(expense_id, user_id)` and
  `expense_item_assignments` PK `(item_id, user_id)` — both ghosts in one
  expense. **Sum** `owed_cents` / `amount_cents` / `weight`; the allocation
  counted the person twice and summing preserves the cent-exact total.
- `group_members` PK `(group_id, user_id)` and `friendships` PK
  `(user_id, friend_id)`, the latter in **both directions** — delete the
  loser's overlapping rows first, repoint the rest, then delete `(A, A)`
  self-loops.
- `settlements` between the two rows — money "paid to oneself", never real.
  Delete, and report the count; it legitimately moves the balance.
- **`activity.audience` is a JSONB array of user ids, not a foreign key.**
  It appears in no FK enumeration; miss it and the merged user's activity
  feed silently breaks.
- Splits on **soft-deleted** expenses repoint too, or restoring one breaks.

Assert inside the transaction that the survivor's post-merge net equals
old-A + old-P with removed self-settlements netting to zero — that assertion
is what catches a mistake before it becomes wrong money. Tombstone the
absorbed row via `merged_into` rather than deleting it, as insurance against
an unenumerated reference.

**Layering exception.** The merge spans users, expenses, groups and social
tables in one transaction. Splitting its SQL across four domain repos to
satisfy the per-domain rule would make it less safe, so it lives whole in
`server/auth/repo/accountMerge.repo.ts` with orchestration and the balance
assertion in `server/auth/usecase/accountMerge.usecase.ts`. Noted in
AGENTS.md as a deliberate exception.

**Preview and confirm is mandatory.** Phone entry is unverified until
tranche 4, so the confirmation screen is the only guard on the merge: it
names what would be absorbed ("4 expenses with Rahul and Priya, $87"). It
is *also* the only defense against a hazard verification cannot cover —
carriers recycle numbers, so proving control today does not prove control
when the invites were made. Someone who does not recognize the counterparty
names backs out and nothing merges.

**Interim exposure, accepted knowingly:** until tranche 4, anyone who knows
a phone number and guesses it was invited can absorb that ledger. Acceptable
with nothing deployed; tranche 4 closes it.

### As built (tranches 2 and 3, 2026-07-27)

Two deviations from the sketch above, both deliberate:

- **Phone is not a field on `UpdateProfile`.** Claiming a number can answer
  with a merge preview instead of an updated user, and one RPC cannot return
  two shapes. It became `SetPhone` → `SetPhoneResponse { user | pending_merge,
  merge_token }` plus `ConfirmPhoneMerge`. `UpdateProfile` keeps name,
  currency and handles.
- **The merge token was needed a tranche early.** It exists to carry a
  confirmation between two RPCs, which is just as necessary when the preview
  comes from an unverified number as when it follows an SMS code. It is an
  HMAC over `keeper.loser.phone.expiry` using the session signing key, so
  there is no table and no sweeper, and it cannot be replayed against a
  different row or by a different account.

`ConfirmPhoneMerge` re-reads the row and re-checks it rather than trusting the
token: the rightful owner may have signed in during the seconds the preview
was on screen, and absorbing it then would take a live account.

**A constraint that only a real database catches.** The merge hands the
absorbed row's phone to the keeper and tombstones it. Done as two statements,
the row is momentarily left with neither email nor phone nor `merged_into`,
and `chk_users_has_identifier` rejects it — every merge fails. The mocked unit
tests passed throughout; `accountMerge.integration.test.ts` (real Postgres,
skips itself when none is reachable) failed on the first run and is the reason
surrendering the phone and stamping `merged_into` are now one UPDATE.

That test seeds every hazard simultaneously — two rows in one expense, one
item assigned to both, overlapping group membership with mismatched roles,
friendships in both directions plus the pair that would become a self-loop, a
settlement between the two rows, a soft-deleted expense, a JSONB audience
naming both — and finishes by asserting that no table anywhere still
references the absorbed row.

**`sessionUserId` was fixed while the layout guard was open.** It verified
signature and expiry only, so a cookie invalidated by signing out everywhere
still rendered the app shell before every RPC inside it failed. It now goes
through `sessionUser()`, which checks the embedded `token_version` against the
row and rejects tombstones, and returns the whole user so the layout can read
`onboarded` from the same query.

### Country picker on the phone field

Onboarding asked for a phone number in one free-text box and leaned on
`DEFAULT_PHONE_REGION` to fill in the missing country, so "4015379205" quietly
became a US number and everyone outside the US had to know to type "+880"
themselves. The fix is the control every product uses for this: country on the
left, national number on the right.

- `lib/phone/phone.ts` builds the country list from libphonenumber-js metadata
  (already a dependency for the server's `normalizePhone`) rather than shipping
  a hand-maintained table that would rot. Flags are derived from the ISO-3166
  alpha-2 code by mapping letters to regional-indicator code points; names come
  from `Intl.DisplayNames`, with the region code as the fallback.
- `components/ui/PhoneField.tsx` is a searchable combobox, not a `<select>`: a
  native select shows the same string collapsed as in its list, so 240 options
  force a choice between an unreadable trigger and a list you cannot scan. The
  listbox filters on country name, dial code and region code through the shared
  `matchesTerms`, so "bang", "880" and "BD" all find Bangladesh.
- The client composes E.164 and the server still validates it. No parsing rule
  moves to the browser — `normalizePhone` stays authoritative, and an explicit
  `+<country>` was always honoured there anyway.
- Pasting a full "+8801…" into the number box re-derives the country instead of
  concatenating onto the selected one, which is the failure mode of every
  picker that treats the two halves as independent.

Kept in `apps/web/src/lib/` rather than `@haalkhata/shared`: the admission rule
is "genuinely needed by both apps", and mobile's phone fields have not moved to
this control yet. It graduates when they do.

### Profile pictures (2026-07-27)

`users.avatar_url`, taken from the ID token's `picture` claim. **No Google
Console change**: `picture` belongs to the `profile` scope, which sign-in
already requests for `name` — the claim was arriving on every sign-in and
being discarded. No new scope, no consent change, no new authorized origin
(JavaScript origins govern where the button runs, not where images load).

It is a hotlink to Google's CDN, not a stored image. This app persists no
blobs at all — receipt photos are processed and deliberately never written —
and one optional avatar is not worth becoming the first thing that does.
Uploads would mean a storage layer, resizing, deletion and moderation.

**Initials remain the real fallback, not a legacy path.** `avatar_url` is
empty for everyone invited rather than signed in, Google documents the claim
as never guaranteed, and the URLs are not contractually stable — so `Avatar`
also falls back on an image that fails to load. Refreshed on every sign-in
when it differs, since a URL stored once and never updated eventually 404s;
an absent claim never clears a stored one.

`<img>` rather than `next/image`, to avoid a `remotePatterns` entry for a
32px square. The one real argument the other way is that next/image would
hide viewers' IPs from Google; `referrerPolicy="no-referrer"` limits the rest.

### Phone verification (tranche 4)

Twilio Verify, last, because it needs an account set up. Two RPCs
(`StartPhoneVerification`, `ConfirmPhoneVerification`) and **no new table** —
Verify holds the pending code, so we never store or hash one. Verify also
requires no A2P 10DLC registration or sender provisioning, which is the
whole reason to use it over Programmable Messaging for OTP. ~$0.058 per
verification (US), fired once per person, so cost is negligible.

Because the code is consumed on check, `ConfirmPhoneVerification` cannot
also be the merge confirm step. It returns the preview plus a short-lived
`merge_token` signed with the existing `sign()` HMAC — same idiom as session
tokens, no new table — which `ConfirmPhoneMerge` presents.

**Rate-limit both RPCs, per user and per IP** (`rateLimitCheck`). OTP
endpoints are the classic SMS-pumping target: attackers trigger codes to
premium-rate numbers they profit from. Twilio's fraud guard helps; our own
limit is what caps the bill.

**Prevention worth taking whenever the invite flows are next touched:** ask
for both identifiers at invite time and backfill the missing one, so the
fork stops forming. If the email matches one row and the phone another, that
is an unverified third-party claim that they are the same person — do not
merge on it, but surface it in the preview.

## 5. Core Domain Logic (usecase/domain — pure, unit-tested)

- `allocate(total, weights)` — largest-remainder allocation; splits always
  reconcile to the exact cent total, deterministic remainder assignment.
- Split calculators: equal / exact (validate sum) / percent (basis points,
  sum=10000) / shares / itemized (Σ assigned items + proportional tax + tip).
- Pairwise balances: per-expense net (paid − owed) matched deterministically
  into debtor→creditor entries; settlements subtract; normalize per pair.
- Simplify debts: greedy min-cash-flow over net balances.

## 6. AI Receipt Pipeline (usecase/receipt + provider adapters)

Upload photo → `ParseReceipt` RPC → provider failover chain (config env
`RECEIPT_AI_PROVIDERS`, default `compatible,mock`) → normalized `ParsedReceipt {merchant, date,
currency, items[], subtotal, tax, tip, total}` → editable review/assign UI →
saved as `split_type=itemized` expense. AI output is never auto-committed.
The `compatible` provider speaks the OpenAI-compatible vision wire format
(swap base URL); the `anthropic` provider uses the Claude API with a strict
JSON schema.

## 6b. Receipt provider + data retention (v5.3 — 2026-07-26)

**The deploy target is a commodity VPS with no GPU.** That kills the original
"self-hosted vision box" plan — Qwen2.5-VL needs ~16GB of VRAM we will not
have. "No vendor lock-in" was always about swappable interfaces and a plain
connection string; self-hosting Postgres is trivial, self-hosting a 7B VLM is
a different category of problem. The provider must therefore be hosted.

**Images are never stored.** Receipt bytes arrive over `ParseReceipt`, live in
memory for one request, and are discarded — there is no image column in any
table, no object store and no filesystem write. Only the extracted structured
data is persisted. The entire privacy exposure is therefore transit plus
whatever the model provider retains, which is what drives the decision below.

**Decision: route tier one through OpenRouter with zero data retention
enforced.** Receipts are other people's financial records. Of the available
paths:

- Anthropic ZDR needs a negotiated enterprise agreement and is not offered on
  pay-as-you-go — closed to us at this size (default is 30-day log retention).
- Gemini's paid tier does not train on inputs but still logs them for a
  limited period; the free tier is used to improve Google's products and may
  be read by reviewers — **never acceptable for this data**.
- Self-hosting is closed by the deploy target.
- OpenRouter can enforce ZDR account-wide, per model group, or per request,
  routing only to zero-retention endpoints, with `data_collection: deny`
  blocking providers that store or train on inputs.

So the `local` provider is renamed **`compatible`** — it was never a
local-model provider, it is an OpenAI-compatible one — and points at
OpenRouter. Env: `COMPATIBLE_AI_BASE_URL` / `_API_KEY` / `_MODEL` / `_ZDR`.
`_ZDR=true` adds `zdr: true` to the request body; it is opt-in because the
field is OpenRouter-specific and a stricter OpenAI-compatible server could
reject an unknown key. Enforcing ZDR account-wide in OpenRouter is the safer
belt-and-braces setting since it fails closed.

Caveats that stay true: the guarantee is the union of OpenRouter's setting and
the destination endpoint's own policy (two parties to audit); ZDR eligibility
is per endpoint, not per model, so the model pool shrinks; and ZDR constrains
retention after processing, not the fact that the image left our server.

**One provider, no vendor SDKs.** OpenRouter fronts every model worth using
here — Claude and Gemini included — so the Anthropic SDK and its separate key
were removed; picking a model is a `COMPATIBLE_AI_MODEL` change, and an
escalation tier is a second model name through the same endpoint rather than a
second client. Default order is `compatible,mock`, with `mock` last so an
unconfigured dev environment still demos the flow.

**Model: `google/gemini-3-flash-preview`,** chosen on price/performance across
all 16 ZDR-eligible providers. The live OpenRouter catalogue (343 models) was
filtered to vision + structured-output + ZDR-eligible (`?zdr=true` cuts it to
224), leaving 100 candidates, then scored on Roboflow Vision Evals. Receipts
need both document axes, so score = mean(Data Extraction, OCR).

Efficient frontier — each row beats everything cheaper:

  $/receipt  score  extract   ocr    $/extra pt  model
   0.00154   81.40   78.3%   84.5%      base     qwen/qwen3.5-27b
   0.00184   87.35   86.6%   88.1%    $0.00005   qwen/qwen3-vl-235b-a22b-instruct
   0.00245   89.05   90.7%   87.4%    $0.00036   google/gemini-3.5-flash-lite
   0.00315   92.25   96.9%   87.6%    $0.00022   google/gemini-3-flash-preview  <- chosen
   0.00945   92.95   94.8%   91.1%    $0.00900   google/gemini-3.5-flash
   0.01260   93.70   94.8%   92.6%    $0.00420   google/gemini-3.1-pro-preview

The cliff sits immediately after this model: reaching it costs $0.00022 per
quality point, the next step $0.00900 — 41x worse marginal value. It also holds
the highest Data Extraction score on the whole board (96.9%), beating models
17x its price, and extraction is our task.

Everything expensive is dominated on mean score: `claude-opus-4.8` ($0.02750)
and `claude-sonnet-5` ($0.01100) both score 90.70 — below this model's 92.25;
`gpt-5.5` ($0.03150) scores 89.40; `kimi-k3` ($0.01650) 88.75. Paying ten times
more buys a worse receipt reader.

Accepted trade-off: OCR is 87.6% (mid-pack) against best-in-class extraction.
The reconciliation check catches misread digits, and the escalation tier is
chosen to cover exactly that gap.

Escalation tier: **`anthropic/claude-sonnet-5`** ($0.01100, 91.7% OCR) — targets
tier one's weak axis, from a different vendor so failures decorrelate rather
than repeat. NOT `claude-opus-4.8` ($0.02750, 93.8% OCR): 2.5x the price for
2.1 OCR points, and it only fires on reconciliation failure anyway.

Budget: ~$2.40/month at 500 scans with 15% escalating. GA-only alternative if
preview status is unacceptable: `gemini-3.5-flash-lite` ($0.00245, score 89.05).

Considered and rejected: specialist OCR models (GLM-OCR, PaddleOCR-VL) beat
every frontier VLM on raw OCR, but GLM-OCR is absent from OpenRouter and the
GLM vision models present (including `z-ai/glm-5v-turbo`) lack structured-output
support. Caveat: Gemini 3.x bills thinking tokens at the completion rate — keep
reasoning effort minimal.

Concrete proof that endpoint-level ZDR eligibility matters:
`qwen/qwen3-vl-32b-instruct` is on OpenRouter but is **not** ZDR-eligible, and
`anthropic/claude-fable-5` holds the board's best OCR (94.0%) yet requires
30-day retention, so both are unusable here despite being strong document models.

## 6d. Image normalization (v5.5 — 2026-07-26)

**iPhones shoot HEIC by default and no vision API accepts it** — not Gemini,
OpenAI or Anthropic. Rejecting it at the allowlist made the scanner unusable
for the most common way a receipt gets photographed; allowing it through
unchanged would only move the failure to the provider.

**sharp cannot decode real iPhone HEIC.** It bundles libheif 1.23, whose
security limits cap an `iref` box at 16 references; actual iPhone photos carry
~48 (HDR gain map, depth map, thumbnails), so all 12 test files failed with
"Security limit exceeded". libheif does not surface that limit through libvips,
and sharp's `unlimited: true` does not reach it. HEIC decoding therefore goes
through **`heic-convert`**, which bundles its own libheif without the cap and
decoded 12/12 at full resolution — pure JS, no system dependency.

`ffmpeg` also decodes these files and was rejected: it returns a half-size
preview image rather than the primary one (1512x2016 against heic-convert's
3024x4032), which is exactly the wrong trade for small receipt print, and it
would add a system package to the image.

Every upload is then normalized with `sharp` before any provider sees it
(`normalizeToJpegBase64` in receipt.usecase.ts). Three things happen, and all
of them matter for receipts:

- **HEIC/HEIF becomes JPEG.** The reason the work exists.
- **EXIF orientation is applied** (`.rotate()` with no argument). Phones record
  rotation as metadata rather than rotating pixels; providers read pixels, so a
  sideways receipt was being transcribed sideways.
- **The long edge is capped at 2576px.** Anything larger is downsampled by the
  model anyway, so sending it only costs upload time and tokens.

This runs for every format, not just HEIC — the orientation fix and size cap
are worth as much on a JPEG straight off a phone. Providers therefore always
receive `image/jpeg`, which also removes a per-format branch from the adapters.

**The client's declared media type is ignored.** Browsers have no MIME mapping
for HEIC and report an empty string for it, so trusting `File.type` rejected
valid iPhone photos before they reached the transcoder — the exact bug this
section exists to fix, hit a second time from a different direction. The server
now sniffs the format from the magic bytes (`detectImageFormat`), which is both
more permissive (accepts files the browser could not name) and stricter (a
`.png` full of script is recognised for what it is). `ParseReceiptRequest.media_type`
is retained on the wire but documented as advisory.

Detection is offset-aware: HEIC is an ISO base media file with `ftyp` at offset
4 and a brand at offset 8, which a from-byte-zero magic comparison cannot
express. The brand is checked against a still-image allowlist so HEIF video
containers (`mp42`) are refused rather than handed to the transcoder.

**Cost of the decision:** `sharp` is a native module, which contradicted the
old "no native modules" line in §7b. That line was about deploy simplicity —
no compiler in the image — and sharp's prebuilt binaries preserve it; §7b is
amended rather than quietly falsified. Adds ~20MB to the image.

Client-side notes: Chrome and Firefox cannot *decode* HEIC either, so the web
picker shows a filename confirmation instead of a broken `<img>` for those
files. On mobile, `PICKER_OPTIONS` sets `quality`, which makes expo-image-picker
re-encode to JPEG — so the client now declares `image/jpeg` rather than
forwarding `asset.mimeType`, which would have labelled already-converted bytes
as HEIC and failed the server's own magic-byte check.

## 6e. The mock provider is not a fallback (v5.7 — 2026-07-26)

Two separate faults made every scan return the mock's "Demo Diner":

1. `dev.sh` started the server with `pnpm --filter @haalkhata/web exec next
   dev`, which runs the Next binary directly and **skips the package's dev
   script** — the only place `--env-file-if-exists=../../.env` is passed. The
   server ran with none of .env set (confirmed from `/proc/<pid>/environ`): no
   OpenRouter key, no SESSION_SECRET, and Postgres only via the built-in
   default, which is why nothing else looked broken. dev.sh now invokes node
   with the env file the same way the dev script does.
2. `providerChain()` kept `mock` as a trailing fallback, so a missing key — or
   a 401, or any provider error — silently produced a plausible fake receipt.

The mock is now used **only when no real provider is configured at all**, never
after one fails, and using it logs a warning. A misconfigured or failing
provider surfaces as an error. Verified live both ways against OpenRouter with
a real iPhone HEIC: correct key → `compatible`, merchant "Zazie", $43.45;
deliberately broken key → throws the 401 rather than returning Demo Diner.

## 6c. Configuration: one .env (v5.4 — 2026-07-26)

There were two `.env` files — repo root for `docker compose` substitution, and
`apps/web/.env` for Next's dev-time loader — because neither runtime can read
the other's file. Six of seven variables were duplicated across them, including
the API key, so a rotated secret had to be changed in two places or dev and
prod would silently disagree.

**Now a single `.env` at the repo root.** Compose reads it via `env_file:`;
`pnpm dev` / `build` / `start` / `db:migrate` load it with Node's
`--env-file-if-exists=../../.env` (Node 20.12+, no dotenv dependency). Real
shell variables still take precedence over the file, so a one-off
`DATABASE_URL=… pnpm dev` overrides it.

The only value that legitimately differs between the two runtimes is
`DATABASE_URL` — `localhost:5432` on the host, `db:5432` inside the compose
network — so compose keeps a one-line `environment:` override, which beats
`env_file:`. Side effect: `pnpm db:migrate` now reads the same connection
string as the app, fixing a stale hardcoded fallback that no longer
authenticated.

**Production should use Docker secrets, not this file.** `SESSION_SECRET`,
`POSTGRES_PASSWORD` and `COMPATIBLE_AI_API_KEY` belong in secrets; the `.env`
is a dev convenience and a template for what a deployment must supply.

## 7b. Deployment (self-hosted Docker)

- `Dockerfile` (repo root): multi-stage — pnpm install → `buf generate` →
  `next build` with `output: "standalone"` → slim runtime image running
  `node apps/web/server.js`. One native module: `sharp`, which ships prebuilt
  binaries (including musl for node:alpine) so the image still needs no build
  toolchain — see §6d.
- `docker-compose.yml` (repo root): `db` (postgres:17-alpine, named volume,
  healthcheck) + `web` (built image, `DATABASE_URL` pointing at `db`,
  port 3000). Secrets come from the host `.env` (see `.env.example`).
- Local dev: `docker compose up -d db` then `pnpm dev` — or point
  `DATABASE_URL` at any Postgres you already run. Pending migrations from
  `apps/web/migrations/` apply automatically on boot; the runtime image
  ships the migrations folder so containers self-migrate on start.
- TLS/domain: see §7c — no longer out of scope, the repo now carries its own
  production compose file and Caddy config.

## 7c. Production deployment (v5.19 — 2026-07-27)

§7b describes the *dev* compose stack. Running it on a public box needs more
than a reverse proxy bolted on, so production is now its own set of files,
committed rather than improvised on the server.

**Separate compose file, not an override.** `docker-compose.prod.yml` is
standalone. Compose merges list keys by appending, so an override file cannot
*remove* `docker-compose.yml`'s published ports — and silently publishing
Postgres on a public interface is exactly the mistake worth designing out. The
prod file publishes nothing but Caddy's 80/443; `db` and `web` are reachable
only over the compose network.

**Secrets are files, not environment.** `SESSION_SECRET`, `POSTGRES_PASSWORD`
and `COMPATIBLE_AI_API_KEY` arrive as Docker secrets under `/run/secrets/`.
(Superseded by §28: the app now reads the files itself through `*_FILE`
variables and the entrypoint exports nothing.) At the time the app read
`process.env`, so `ops/docker-entrypoint.sh` bridged the two and
assembled `DATABASE_URL` there — meaning the password appeared in no compose
file, no image layer, and no `docker inspect` output. It does still reach the
process environment, because that is what the app reads; closing that last gap
means teaching `auth.usecase.ts` and `receipt.constants.ts` a `*_FILE`
convention, which is worth doing but is not what stands between here and a
deploy.

**Misconfiguration fails closed.** If the entrypoint cannot read
`postgres_password`, `DATABASE_URL` is never exported, the app falls back to
`DEFAULT_DATABASE_URL`, and `assertSafeDatabaseUrl()` throws — production
rejects the default credential (§AGENTS "Production guardrails"). A missing
`SESSION_SECRET` throws for the same reason. The container then fails its
healthcheck and `docker compose up -d --wait` fails the deploy, so a
misconfigured release never becomes a running one.

**The reverse proxy carries two load-bearing lines.** `Caddyfile` is not
boilerplate:

  - `header_up X-Forwarded-For {remote_host}` — `clientIp()` in
    `auth/handler.ts` reads the *first* comma-separated value of
    `X-Forwarded-For`, and Caddy by default *appends* the real peer to
    whatever the client sent. Without the overwrite, a caller supplies their
    own header, picks their own rate-limit bucket, rotates it freely, and
    `AUTH_RATE_LIMIT` stops meaning anything.
  - Host is deliberately *not* rewritten — `csrfGuard()` compares the `Origin`
    header's host against `request.headers.host`. Caddy preserves Host by
    default; nginx would need `proxy_set_header Host $host` or every browser
    POST 403s.

The CSP allows `'unsafe-inline'` in `script-src` because Next's App Router
emits inline hydration scripts and per-request nonces need a `middleware.ts`
the repo does not have. The four `accounts.google.com/gsi/*` entries are
Google's documented requirement for the Sign In With Google button; drop any
one and the button silently fails to render (§4c).

**CI builds, the server only pulls.** `.github/workflows/ci.yml` runs the
gates; `deploy.yml` builds the image on amd64, pushes it to GHCR, and hands
the server a commit SHA over SSH. The deploy key is installed with a forced
`command=` in `authorized_keys`, so it cannot open a shell, forward a port, or
run anything but `deploy.sh` — which validates its argument is a bare 40-char
SHA before touching anything. Rollback is the same command with an older SHA.

`NEXT_PUBLIC_GOOGLE_CLIENT_ID` is inlined by `next build`, so it is a build
arg fed from a repo *variable*, not a runtime value. Setting it only at
runtime produces an image whose Google button never appears — and since
`passwordAuthEnabled()` is false in production (§4c), that is a total lockout,
not a degraded experience.

**Host expectations.** Ubuntu 26.04 LTS or Debian 13; app and Postgres

## §21 Simplify debts becomes a real group mode

**Problem.** The "Simplify debts" toggle was client-side `useState` — not
persisted, per-viewer, per-visit. Its settle buttons dead-ended: a simplified
edge (A pays C for a debt that pairwise runs A→B→C) usually has no pairwise
counterpart, so the settle modal found nothing owed and the server guards
(`amountOwed`/`owedByScope`, both pairwise) would refuse anyway. And making
those guards accept simplified edges *alongside* pairwise ones would let the
same debt be paid down both routes — the friends/groups double-count all over
again. Two debt graphs over the same nets can never both be live.

**Design.** `groups.simplify_debts boolean` — a persisted, group-level mode,
Splitwise semantics. Nets are identical in both modes; balances stay fully
derived; settlement rows are unchanged. The mode only decides how a group
scope *routes* debt between members — the raw pairwise graph, or the
min-cash-flow graph over the same nets — and every consumer follows it:

- `amountOwed` / `owedByScope` (settlement validation + allocation) read the
  routed edge, so exactly one payment path exists per cent of debt, in either
  mode, race-guarded by the existing per-pair lock.
- `getFriendLedger` group rows, `getOverallBalances`, `netWithUser` route the
  same way, so the dashboard, friends list, settle checklist and group page
  can never disagree about who owes whom. Rerouted rows carry a `simplified`
  flag (FriendGroupBalance.simplified) so the UI can say why.
- The friend page's history stays the pair's true shared history; when a
  simplified group makes the headline differ from the running total, the
  caption says so instead of pretending.

Toggling is member-level (same trust as AddMembers), idempotent, writes a
group-wide activity entry, and rewrites nothing — flipping modes only changes
routing, so it is always safe. Turning it off after simplified payments can
surface pairwise cycles that net to zero; the balances panel explains them
rather than hiding them. RPC: `GroupService.SetSimplifyDebts` (additive).

## §23 The feed is personal: transactions reach their participants only

If you are A, "B paid C" is B and C's feed line — a transaction that moved
none of your money does not show up in your activity, global or group tab.
Enforced in the audience, which was already the read-path filter:

- Write path: expense events (added/updated/deleted) and their comments are
  announced to the expense's participants plus the actor; settlements to
  the pair. Structural events (group_created, member_added, simplify_debts)
  stay group-wide — those genuinely involve everyone.
- Read path: the group-scoped feed query previously filtered by group_id
  alone, showing members everything; it now requires audience containment
  in both scopes — a group id narrows *where*, never *who may see*.
- Data migration (1784764800000) trims historical wide audiences: expense
  and comment rows join exactly via their /expenses/<id> link; settlement
  rows use (actor, credit_user) where those differ, and fall back to the
  amounts-backfill adjacency match against the settlements table.

The group's ledger tabs (expenses list, balances) are unchanged — members
still see the whole ledger; the feed is the personal narration of it.

## §24 Time: stored UTC, spoken local

Storage was always UTC (TIMESTAMPTZ) — the display was the problem: pg's
type parser passed Postgres's own text form ("2026-08-09 00:38:12+00") to
browsers, several screens rendered its raw UTC date with .slice(0, 10), and
the new-expense form prefilled UTC's today (tomorrow, for an evening user
west of Greenwich).

- Boundary: the TIMESTAMPTZ parser now emits ISO 8601 UTC ("…T…Z") — the
  one shape every engine parses — so clients can always convert. Storage
  unchanged; only the spelling.
- Display: packages/shared time/localTime.ts (localDate, localDateTime)
  renders in the viewer's timezone, year only when not current; used by the
  activity lists, dashboards, expense detail comments/history, and the
  friend ledger (whose settlement lines now carry created_at — additive
  FriendLedgerEntry field — because only the client knows the timezone).
- Input: todayISO() is the user's local calendar day now, not UTC's; that
  prefills the expense forms and the scan flow. The server's empty-date
  backstop stays UTC (it cannot know the caller's timezone) and is not the
  path a person's "today" takes.
- Calendar dates (expense_date) are deliberately untouched end to end: the
  user picked a day, not a moment; there is nothing to convert.
- Known coarseness: the activity month filter buckets by UTC month
  server-side; events within hours of a month boundary can file under the
  neighbouring month. Fixing it needs the viewer's timezone on the RPC —
  deferred until someone actually trips on it.

## §25 Closing the client half of the security audit (2026-08-29)

The 2026-08-23 audit (SECURITY-AUDIT.md) was worked through as one commit
per finding. Reviewing those commits showed a pattern: the server rule
landed, the clients did not — a control the server now refuses stayed on
screen, a promise the server no longer keeps stayed in the copy. This section
records what was completed, so the contract and the two apps say the same
thing.

- **A settled expense can still be corrected — or deleted.** The audit asked
  for edits to be serialized against settlements and for deletion of a
  settled expense to be refused; the first pass froze edits too, which turned
  "B paid, then somebody spotted a mistake" into a fake compensating expense
  (negative amounts are not allowed, so a refund had to be modelled as an
  expense the other way round). Edits now run under the ledger lock and the
  derived balance rebalances against what was already paid — pay less than
  your corrected share and you are owed the difference, more and you owe it.
  Deletion is allowed for the same reason: delete means owed-to-zero, the
  payment stays, and the payer is owed a refund. What made deletion look
  dangerous was that a deleted expense vanished — every list dropped it, its
  page 404'd, the friend ledger could not carry it — so the refund appeared
  from nowhere. Deleted expenses now stay visible everywhere the ledger is
  shown (`Expense.deleted_at`, `FriendLedgerEntry.deleted`): struck through,
  contributing nothing, never "settled", read-only, with "deleted by X on Y"
  on the detail page from the `expense_deleted` activity row that now links
  there. `GetExpenseResponse.has_later_settlement` is a warning before either
  change, not a lock.
- **Anyone on an expense may correct it.** Editing was creator-only, so a
  participant who spotted the mistake had to ask whoever entered it. Now the
  creator, every payer and everyone who owes a share may edit (the "updated"
  activity reaches all of them); deletion stays with the creator, since it
  is the destructive direction and leaves nothing behind to check. Both
  clients show Edit to participants only and Delete to the creator only —
  the buttons the server denies are never offered.
- **Leaving a group is reachable.** RemoveMember lets a zero-balance
  non-owner remove themselves (§3i); the members list on both apps now has
  "Leave group" on your own row and "Remove" on every other row for the
  owner. The shared `group/roles.ts` spells the owner role once.
- **Add-people no longer promises a shadow account** (§3i, revised).
- **Private contact fields stay private in the UI.** Search matches names
  only; the friend header shows sign-in state instead of an empty line.
- **Text bounds are one constant** — `@haalkhata/shared/text/limits.ts` —
  re-exported by the server's domain constants and applied as `maxLength` on
  every bounded input in both apps, so a client stops at exactly the length
  the server (and the matching database CHECK) accepts.
- **A refused ledger read is shown as refused.** The dashboard and friends
  screens render the server's rate-limit message instead of a zero balance
  or an empty friends list.
- **Categories:** the server allowlist is the shared `CATEGORIES` list plus
  the legacy `lodging`/`other`, and the database CHECK matches; picker
  choices are stored verbatim instead of flattened to "general".

Server-side corrections made in the same pass: one-off ledger locks are per
participant rather than per pair (the pair set overflowed Postgres's shared
lock table at large casts); the server-component session guard parses the
Cookie header with the same duplicate-rejecting parser as Connect; the text
and currency constraint migration normalizes legacy rows before adding its
CHECKs; the backup-failure notifier is allowed AF_UNIX so `logger` no longer
kills it before the HTTPS alert; and Caddy strips `X-Real-IP`.

Still open from the audit, deliberately: the mobile app has no Google
sign-in (password RPCs are disabled in production, so a release build cannot
sign in — a feature, not a fix); ListGroups / ListExpenses /
GetGroupBalances / GetFriendLedger are as expensive as the rate-limited
reads and remain unlimited; and group-scope immutability is group-wide after
any settlement — narrowing it needs a stored `simplified` flag on
settlements.

## §26 The friction pass (2026-08-29)

With the audit closed, the question became which rules still cost a normal
user more than they protect. Eight were found; all eight are done.

- **Mobile signs in with Google.** Production accepts Google only, and the
  app only knew the password RPCs — a release build could not sign in at
  all. `expo-auth-session`'s Google provider now runs the same
  server-nonce challenge the web uses, against the platform's native client
  id; the server accepts those ids as audiences (`GOOGLE_MOBILE_CLIENT_IDS`).
  The password form is development-only, mirroring the server.
- **An owner can hand the group on.** `TransferOwnership` makes another
  member the owner and drops the caller to a member, who can then leave —
  the "transfer ownership first" message finally points at something.
- **A mistaken payment can be removed.** `DeleteSettlement` is the same
  visible soft delete expenses got: either person on the payment may remove
  it, the friend-ledger line stays struck through with a zero change, the
  debt it paid down comes back, and the other person is told. Web first;
  mobile caught up in §27 with the friend ledger screen.
- **Editing an expense can change who is on it.** Only the group/one-off
  scope is pinned (settlements live there); the server always accepted a
  changed cast, and now both pickers allow it.
- **Sessions renew themselves.** Past half its seven-day life, any
  authenticated RPC re-issues the token — a cookie for the browser, the
  `x-haalkhata-session` header for mobile — so regular use is never signed
  out; only inactivity or sign-out ends a session. LogOut is exempt.
- **Itemized expenses are editable on mobile.** The scan flow's item editor
  became a shared hook and component (`lib/hooks/useItemDraft`,
  `components/expense/ItemDraftEditor`); the expense form gained an "Items"
  split type that reloads a receipt's lines and assignments.
- **The "somebody has paid" warning is about the expense's own people** in
  pairwise groups; simplified groups keep the wide answer, because there a
  payment between two unrelated members can be routed debt from the
  expense.
- **Comments stay open on a deleted expense** — "why was this removed?" is
  the conversation the kept row exists to host.

Deliberately unchanged: bringing a brand-new person in still takes a friend
request they accept first (the cost of closing the account-existence oracle;
an invite link would soften it), an expense still cannot move between
groups, leaving a group still needs a zero balance, and receipt scanning
stays at five a minute.

## §28 Closing the server half of the security audit (2026-08-30)

§25 closed the client findings of the 2026-08-29 audit. This pass took the
rest — the ledger, the API, secrets and operations — the same way: every
finding re-checked against the code first (two had already been closed on
this branch: mobile Google sign-in, and transfer-ownership's owner check),
then the established way of solving each looked up before choosing ours, and
one commit per finding so a reviewer can take or revert each on its own.
The decisions worth keeping, because the code cannot explain why it is
shaped this way:

- **Side effects commit with the change they announce.** Activity rows,
  notifications and the friendships a group creates are written on the same
  transaction client as the expense, payment or group change they describe.
  The pattern is the transactional-outbox one — but the "outbox" here is
  just more Postgres tables and there is no broker to relay to, so the
  tables themselves are the outbox and the same transaction is enough.
  Repo insert functions take an optional `client` for that reason; a usecase
  that writes a side effect outside the transaction is a bug.
- **Idempotent money mutations.** `CreateExpense` and `RecordSettlement`
  require a client-generated UUID `operation_id` (the IETF Idempotency-Key
  draft's model, as Stripe applies it): the key is claimed inside the ledger
  transaction under the primary key (user, rpc, id), so a concurrent
  duplicate waits on that row and then replays; a replay with the same
  canonical payload returns the stored result, a reuse with a different
  payload is refused, a key whose first attempt is still running says so,
  and claims expire after 24 hours. The clients hold the id in a ref for the
  life of one submit and mint a new one after success, so a retry after a
  timeout cannot double-post and a second intentional payment cannot be
  swallowed.
- **Who asserted a payment is part of the ledger.** Either party can record
  a payment in either direction — that is what makes settling up usable — so
  the trust model is provenance plus reversal, not approval: `recorded_by`
  and `deleted_by` are stored, the feed and the friend ledger say "recorded
  by" whenever the recorder is not the payer, and the counterparty sees it
  immediately and can remove it. An approval step was considered and
  rejected: the app cannot verify a payment happened, so approval would only
  block the honest majority while a dishonest counterparty declines.
  Visibility and an audit trail are what a shared ledger can actually offer.
- **Balances are kept per currency and never summed.** Every balance map
  is keyed by currency (`CurrencyCents`), responses carry `CurrencyAmount`
  buckets ("you owe $12.45 and €8.72"), settlements allocate only within the
  currency being paid, a group's expenses and payments are in the group's
  currency, and nothing ever converts — the Splitwise and ledger-provider
  rule. The old scalar fields stay on the wire because `buf breaking` forbids
  removing them; they are redefined as the caller's default-currency bucket
  and legacy readers see exactly what they saw before when only one currency
  is in play. The account-merge invariant is checked per currency too.
- **The int32 ceiling is a stated limit, not a crash.** Cents stay int32 on
  the wire (changing the type is a breaking change and would put bigints in
  every client); every aggregate goes through `toInt32Cents()` and an
  overflow is a `failed_precondition` naming the ceiling (21,474,836.47 in
  one currency) rather than an encoder exception. Per-row amounts are
  bounded at validation, so only sums can reach it.
- **No payment onto a loop that nets to zero.** With Simplify debts off, a
  group whose pairwise debts cancel around a cycle shows debts while
  everyone is settled overall; the server refuses to record a payment there
  and the clients hide Settle/Record, pointing at Simplify debts instead.
- **Reads are bounded.** The friend ledger stops at 300 lines and the
  expense list at 500, each with a `truncated` flag the clients show; the
  read RPCs that fan out over the ledger are rate-limited at 60/min per
  user. The limiter — like the SMS limiter below — is process-local, which
  is correct for the single-container deployment this is and becomes a
  documented gap the day a second replica exists.
- **SMS is limited by destination and client, not just by account.** Three
  sends an hour and eight a day per number (keyed by an HMAC of the E.164
  number, so the limiter never holds phone numbers) and twenty an hour per
  client address, on top of the per-account limit — Twilio's own anti-fraud
  guidance. Reminders take a (sender, debtor) advisory lock before the
  cooldown check so two clicks cannot both pass it.
- **Secrets are files, and keys can overlap.** `readSecret()` implements the
  Docker `<NAME>_FILE` convention; the entrypoint exports nothing, the
  database URL is assembled from `POSTGRES_*` inside the app, and
  `SESSION_SECRET_PREVIOUS` lets a planned rotation keep sessions valid
  until they expire. CI runs gitleaks over the full history. What is still
  documented rather than automated: the secret inventory and expiry
  monitoring, and separate migration and runtime database roles.
- **Readiness means someone can sign in.** With password auth off, the
  health route refuses when there is no Google audience, when the image
  was built without the public client id, or when the two differ; the
  deploy workflow refuses to build without it and Compose refuses to start
  without it.
- **A backup that stayed on the box is a failed backup.** Missing offsite
  target now fails the run and alerts unless a written local-only opt-out
  is present; every archive is listed back from the remote and its size
  compared after upload.
- Also closed: strict calendar dates (Feb 30 is rejected, not normalized),
  the service worker caches only content-hashed build assets, the bearer
  token is returned only to clients that declared bearer transport, receipt
  provider and decoder errors are logged rather than shown, the currency
  field is an allowlist, the development password floor is eight
  characters with hashing off the event loop, and the mobile query cache
  is memory-only (OWASP MASVS-STORAGE: not writing it beats encrypting it).

Left open on purpose, each a known trade-off rather than an oversight: a
shared rate limiter for a multi-replica deployment; deleting or archiving a
group; an exactly-one-owner database constraint (the usecase enforces it
under the group lock); monitoring for secret age; split database roles; and
a release-mode mobile end-to-end sign-in test. The root `AUDIT.md` predates
§25–§28 and is kept as history, not as a to-do list.

## §29 A readability pass over the backend (2026-08-31)

Before the code grows further, one deliberate pass over everything in

- **One spelling per invariant.** The `friend-request-inbox:` advisory

- **Prose repaired.** An old mechanical rename (key → operation) had

## §31 Server config flows through the deploy pipeline (2026-09-01)

Set on GitHub already: ACME_EMAIL=anirudhaprasun@gmail.com (repo variable).

## §32 Phone verification hardening + phone UX completion (2026-09-01)

Fixes for the seven issues found reviewing the phone flow, following OWASP
ASVS/MASVS OTP guidance (single-use, server-side attempt caps, short expiry,
bind the check to the requester) and Twilio's own anti-fraud guidance.

Server:
1. New `phone_verifications` table — one active verification per account:
   (user_id PK, phone, created_at, send_count, last_sent_at, check_count,
   consumed_at). The check call now requires an active, unexpired (10 min),
   unconsumed row for THIS account matching THIS phone; approval consumes it
   (single-use server-side, no longer relying on Twilio's semantics), and
   check_count caps attempts at 5 our side before Twilio is even called.
   Fixes #1 (binding) and #2 (replay/brute-force ownership).
2. SMS-send abuse ceilings move to Postgres (`phone_send_events`: destination
   hash + client ip + sent_at, pruned on insert like operations): 3/h + 8/day
   per destination and 20/h per IP now survive restarts and replicas. The
   in-memory limiter stays for cheap per-account request pacing. Fixes #3.
3. Split per-account buckets: phone:send 3/min, phone:check 5/min,
   phone:merge 5/min — a fumbled code no longer locks out the confirm. #7.
4. Merge token gains a preview fingerprint (hash of nets+expense_count+name);
   ConfirmPhoneMerge recomputes and refuses on drift ("balances changed —
   review again"), so nobody absorbs materially different history than they
   were shown. Fixes #6.
5. New AuthService.RemovePhone RPC (proto + gen): clears the caller's phone;
   refused when the phone is the row's only identifier
   (chk_users_has_identifier). Fixes #4.
6. Merge preview counterparty list capped (12) and the disclosure logged
   (audit trail); the preview itself is retained deliberately — it IS the
   recycled-number defense. Mitigates #5.

Clients (both): the searchable-country PhoneField already exists (account,
onboarding). Completing coverage: the add-friend and add-to-group forms get
an explicit Email | Phone toggle whose phone side is PhoneField with
client-side isValidPhoneNumber gating (libphonenumber-js, already shipped);
account screens gain Remove-phone. The dev-only password login keeps its
single identifier box: production rejects that flow entirely.

Plus: a Twilio setup runbook artifact for the operator (account, Verify
service, restricted API key, geo permissions, Fraud Guard, secrets wiring).

## §33 Frictionless invites: Invited people, reminder links, group join links (2026-09-02)

Direction from Anirudha: minimize friction. Anyone can add anyone as a
friend or into a group; a person without an account appears as "Invited"
and CANNOT be part of any transaction until they sign up. Inviters get an
easy share-a-link way to remind them; groups get a shareable join link
whose landing page says who invited you to what, and accepting joins you.

The key insight that makes this safe: the no-transaction rule removes all
money from unclaimed rows. An invite that carries no balances can be
claimed via a bearer link without the recycled-number/absorb-history
dangers §32 defends against — claiming an empty identity just wires up
friendships and group memberships.

Design:
1. Invited = the existing shadow-user row (no credential), resurrected as
   a first-class state. `User.registered` already crosses the wire; the
   clients render an "Invited" badge off it.
2. The transaction gate lives in ONE place: expense create/update refuses
   unregistered payers/owers by name ("X hasn't joined yet — remind them
   to sign up"). Settlements and reminders need no new guard: both already
   require outstanding debt, and a no-transaction invitee can never have
   any. Legacy shadows with pre-existing money keep their history and can
   still be settled with; they just can't join NEW expenses.
3. AddFriend(email/phone) with no matching account creates the shadow and
   an immediate two-way friendship (there is nobody to accept). A matching
   REGISTERED account keeps today's request+accept flow. Trade-off knowingly
   accepted: the differing outcomes reveal whether an identifier has an
   account — Splitwise-style frictionlessness beats the oracle here; rate
   limits (10/min) and logging stay.
4. AddMembers email/phone that matches nobody creates the shadow and
   enrols it (Invited member). Registered-but-unconnected stays refused —
   the join link is the path for strangers.
5. invite_links table (raw 43-char random token PK — retrievable so the
   share button always shows the same link; revocable): kind 'friend'
   (inviter + the invited shadow it claims) or 'group' (group_id). One
   active link per (inviter, invited) pair and per group.
6. New social.v1 RPCs (all link kinds live in social — the connective
   tissue — to avoid cross-proto imports): GetFriendInviteLink,
   CreateGroupInviteLink (any member; returns the active link),
   RevokeGroupInviteLink (owner), PreviewInviteLink (UNAUTHENTICATED,
   IP-rate-limited; returns inviter name, kind, group name+member count),
   AcceptInviteLink (authenticated): friend-kind → merge the still-
   unclaimed shadow into the caller (memberships and friendships ride
   along) + befriend the inviter; group-kind → enrol + befriend inviter,
   with feed event and notification. Idempotent re-accepts.
7. mergeAccounts generalizes for link claims: the eligibility check uses
   IS NOT DISTINCT FROM for a NULL phone, and the loser's email moves to
   the keeper when the keeper has none, otherwise is cleared — a tombstone
   must not strand an address the person may later sign up with.
8. Delivery is the inviter's own share sheet (navigator.share / RN Share,
   clipboard fallback) — industry standard for v1; no server-side email or
   SMS sending is introduced.
9. Web landing route /join/<token> (public preview → Google sign-in →
   auto-accept); login gains a `next` redirect if it lacks one. Mobile
   mirrors with an expo-router join/[token] route.

Rollout: migration+proto first, then server (gated), then web, then
mobile, then docs — small commits per phase.

### §33a Profile links: "add me" (2026-09-02)

Third invite-link kind, 'profile': the caller's own shareable link, minted
on first ask, one active per user, revocable. Preview says "X wants to
connect"; ACCEPTING SENDS A FRIEND REQUEST rather than creating the
friendship — the deliberate asymmetry against the other kinds. A friend/
group link's blast radius is bounded (an Invited row holds no money; a
group join is visible to the whole roster), but instant friendship from a
bearer profile link would let anyone who finds it attach themselves to the
owner and start putting them on one-off expenses. The link removes the
typing and the identifier-guessing, not the consent tap. Already-friends
and duplicate requests accept quietly; the owner gets the ordinary
friend_request notification and accepts from Friends like any other.

### §33b Invite-surface hardening (2026-09-03)

Adversarial pass over §33/§33a before Twilio goes live; five fixes:
1. A link-claim no longer adopts the invited row's identifiers. The phone
   was the INVITER'S claim, verified by nobody — promoting it to the
   acceptor's own number squatted numbers their real owners could then
   never attach. mergeAccounts takes an explicit adoptPhone flag: true only
   on the SMS-merge path, where possession was proven seconds earlier;
   email adoption is dropped everywhere (a freed address is reclaimed by
   its owner through Google's verified sign-in, not inherited).
2. Claim links are mintable only by an actual friend of the invited row
   (its inviters), no longer by any co-member: a co-member of group A could
   mint a link and claim the identity with a second account, inheriting
   seats in groups B and C that nobody in B or C consented to.
3. A claim announces itself: after the merge, every inherited group gets a
   member_added feed event ("claimed X's invitation via Y's link"), so a
   roster face never changes silently — the same transparency rule group
   joins already follow.
4. Group joins via link are capped at MAX_GROUP_MEMBERS (100, aligned with
   the expense participant ceiling): a leaked bearer link must not let a
   bot swarm grow a roster without bound.
5. Two acceptors racing one claim link: the loser's merge eligibility
   failure now maps to the generic dead-link sentence instead of leaking a
   500.
Residual, documented: invite tokens ride in URLs and therefore appear in
front-proxy access logs — operator-visible only, and revocation is the
remedy; this is the industry-standard trade for shareable links.

### §33c Groups are registered-only; inviting becomes explicit (2026-09-03)

Direction: nobody who is not on the platform can be added to a group — not
even as an Invited seat. This walks back §33's group-side cold enrolment;
the Invited state now lives ONLY in the friends list. The new group-add
flow: typing an email/phone that has no claimed account refuses with a
distinct failed_precondition ("they're not on HaalKhata yet — invite them
to sign up first"); the client renders that as an offer — "send them a
sign-up invite?" — which creates the Invited friend and hands the caller
the claim link to share. Once they sign up, they are already the caller's
friend and addable like anyone. One server gate enforces it for picked ids
too, inside enrollMembers (covers CreateGroup and AddMembers alike), so an
unregistered friend can never hold a seat going forward. New social RPC
InviteContactToSignUp(email|phone) → InviteLink does the offer's work:
find-or-create the unregistered contact, befriend, mint the claim link.
Deliberate oracle: the distinct refusal says an identifier has no account —
the same §33 trade, now scoped to an explicit user gesture.

### §34 Verified number transfer with dual notification (2026-09-03)

Direction: numbers move (lost SIMs, temporary SIMs). Whoever proves SMS
possession attaches the number — even when a REGISTERED account holds it —
because the phone is a directory pointer and NEVER an authenticator
(sign-in stays Google-only). WhatsApp semantics: possession wins, both
sides are told. SetPhone's claimed-holder branch becomes a transfer: one
transaction locks both user rows (sorted FOR UPDATE), re-checks the holder
still holds it, frees it, attaches it, and notifies BOTH parties
(phone_transferred: the loser learns the number now points elsewhere and
how to take it back or object; the gainer learns it was taken from another
account). Refused only when the number is the holder's sole identifier
(dev phone-signup rows — clearing it would strand the account). The
clients mark the saved number "Verified" — every attached number is, by
construction.

### §35 Stored phone verification state (2026-09-06)

§34's closing line — "every attached number is verified by construction" —
is only true for numbers written after §32. Production rows predate it:
their numbers were written by the old unverified SetPhone and are
indistinguishable in the schema, yet the clients would show them the
verified chip. Fix: store the fact instead of inferring it. New column
users.phone_verified_at (TIMESTAMPTZ, null = unverified), backfilled NULL
for everyone — honest, since Twilio was never configured before this.
setUserPhone stamps now() on set and clears on clear (all its callers are
SMS-proven contexts); the merge's adoptPhone stamps only when the number
actually adopts into the empty slot; the tombstone clears it. Shadow-row
creation (inviter-typed numbers) leaves it NULL by default. A CHECK keeps
the pair coherent (no stamp without a number). Exposed as the private
`phone_verified` field on common.User (self-view only, like phone). The
clients stop lying: the chip reads the field, an unverified number gets a
"Verify" action that re-runs SetPhone on the number already held (the
self-holder path), and a dismissible post-login banner prompts legacy
holders — soft, not a wall, because phone stays optional; its honest pitch
is §34 itself: verify it or anyone proving SMS possession can claim it.

### §36 Full ISO 4217 currency catalog (2026-09-06)

The 8-code allowlist becomes the full ISO 4217 catalog (currency-codes
package for codes/names/minor-unit digits, currency-symbol-map for
symbols), minus the non-transactional codes (metals, funds, SDR, test).
Pickers show the symbol beside the code and name; the familiar 8 stay
pinned to the top, the rest alphabetical. Web keeps native selects, mobile
replaces the chip row with a searchable picker sheet. Money helpers become
minor-unit aware: amounts stay integers in the currency's own minor unit,
so formatMoney/parseMoneyInput/centsToInput take the currency's digits (0
for JPY, 3 for KWD) instead of assuming 2; display can no longer round a
yen amount into a lie. Two facts confirmed, now documented as invariants
rather than accidents: a group's currency is declared at creation and
frozen (no RPC or SQL path updates it; it is the unit every balance in the
group derives in), and positions are kept and shown per currency, never
summed across currencies.
